# AX1 통합 스킬팩 구조와 로드맵

AX1 통합 스킬팩은 사업계획서뿐 아니라 보고서, 제안서, 발표자료, 매뉴얼, 명세서와 관리대장 등 팀의 반복 산출물 업무를 에이전트와 함께 수행하기 위한 공통 업무 체계다. 기존 AX1 Bizplan은 폐기하거나 한 번에 교체하지 않고, 통합 스킬팩의 첫 번째 전문 업무 모듈로 유지·발전시킨다.

이 문서는 통합 스킬팩의 목표 구조, 기존 기능과의 관계, 단계별 전환 순서와 운영 기준을 정의한다. 현재 구현된 기능과 향후 계획을 구분하며, 실제 릴리즈 범위와 시점은 각 단계의 검증 결과에 따라 배포자가 결정한다.

관련 기반 설계:

- [AX1 공통 정책 분류와 전환 인벤토리](ax1-common-policy-inventory.md)
- [`ax1-work` 통합 진입 스킬 설계](ax1-work-design.md)

## 1. 한눈에 보기

### 목표

- 팀원이 산출물 종류에 맞는 스킬 이름을 몰라도 하나의 AX1 진입점에서 작업을 시작할 수 있게 한다.
- 모든 산출물에 사용자 이해 확인, 자료 우선순위, 한글 원문 보존, 버전·최신본 관리와 검증 원칙을 동일하게 적용한다.
- 사업계획서, 보고서, 제안서처럼 업무 논리가 다른 영역은 독립 모듈로 나누어 정확성과 유지보수성을 확보한다.
- HWPX, DOCX, PPTX, XLSX와 PDF 같은 파일 형식 처리는 내용 작성과 분리해 여러 업무 모듈이 재사용하게 한다.
- 전체 설치와 개별 스킬 설치가 같은 동작을 제공하고, GitHub 계정이 없는 팀원도 Release ZIP으로 설치·업데이트할 수 있게 한다.

### 권장 형태

```text
AX1 통합 스킬팩
├─ 공통 코어             모든 작업에 적용되는 정책·검증·자산
├─ 통합 진입점           요청 분류, 질문, 작업 경로 선택
├─ 업무별 스킬           사업계획서, 보고서, 제안서, 매뉴얼 등
├─ 문서 형식 엔진        HWPX, DOCX, PPTX, XLSX, PDF
└─ 운영·배포 체계        설치, 업데이트, PR, 검증, 릴리즈
```

통합은 모든 지침을 하나의 거대한 `SKILL.md`에 넣는다는 뜻이 아니다. 공통 규칙은 한 곳에서 관리하고, 사용자 요청은 작은 전문 스킬로 연결하며, 각 스킬은 개별 ZIP으로 설치해도 독립적으로 동작해야 한다.

## 2. 상태 표기

이 문서에서는 기능 상태를 다음처럼 구분한다.

| 상태 | 의미 |
|---|---|
| 현재 | 현재 안정 배포 또는 저장소에 이미 존재하는 기능 |
| 진행 중 | 설계 또는 구현이 시작됐지만 아직 안정 배포되지 않은 기능 |
| 다음 | 통합 스킬팩 기반 단계에서 우선 구현할 기능 |
| 후보 | 팀 사례와 사용 빈도를 확인한 뒤 구현 여부를 결정할 기능 |

로드맵에 이름이 적혀 있어도 `다음`이나 `후보` 상태의 스킬은 아직 설치하거나 호출할 수 있는 기능이 아니다.

## 3. 설계 원칙

### 3.1 사용자 확인 후 작업

모든 AX1 스킬은 실제 작업 전에 에이전트가 다음 내용을 먼저 설명한다.

- 이해한 목적
- 예상 입력자료와 기준 문서
- 작업 범위와 제외 범위
- 예상 산출물
- 주요 가정과 위험

사용자가 이를 확인하고 별도 메시지로 동의한 뒤에만 파일 조회, 도구 실행, 작성과 수정에 들어간다. 작업 중 목적·대상·산출물이 실질적으로 바뀌면 변경된 이해 내용을 다시 확인한다.

### 3.2 하나의 진입점, 작은 전문 모듈

통합 진입점은 요청을 분류하고 적절한 전문 스킬을 선택한다. 사업계획서 작성, HWPX 편집, 제출 전 검토 같은 전문 판단을 통합 진입점에 중복해서 넣지 않는다.

새 스킬은 다음 조건을 만족할 때만 만든다.

- 사용자가 구분해서 요청할 수 있는 독립 목적이 있다.
- 입력자료, 판단 기준 또는 산출물이 기존 스킬과 뚜렷하게 다르다.
- 기존 스킬의 모드 추가만으로는 설명과 검증이 지나치게 복잡해진다.
- 독립 라우팅과 독립 테스트가 장기 유지보수에 유리하다.

### 3.3 내용과 파일 형식의 분리

업무별 스킬은 무엇을 왜 작성할지 결정하고, 문서 형식 엔진은 확정 내용을 특정 파일 형식에 안전하게 반영한다.

```text
사용자 요청
  → 업무 목적·독자·양식·근거 확인
  → 내용 구조와 확정 브리프 작성
  → HWPX·DOCX·PPTX·XLSX 엔진 선택
  → 구조·내용·레이아웃 검증
```

업무 판단과 파일 조작을 분리하면 같은 결과보고서 내용을 HWPX와 DOCX로 만들거나, 확정된 사업계획서 핵심 내용을 발표자료로 연결하기 쉬워진다.

### 3.4 공식 양식과 원문 우선

- 공식 양식, 공고문, 계약상 요구사항과 사용자의 명시적 지시를 일반 기본값보다 우선한다.
- 한글은 유니코드 이스케이프, 숫자 문자참조, 영문 음역 또는 ASCII 대체로 바꾸지 않고 실제 한글 문자로 기록한다.
- 체크박스, 선택 상태와 의미 있는 기호는 승인 없이 다른 문자로 바꾸지 않는다.
- 근거가 부족한 수치, 기관 역할, 일정과 성과를 사실처럼 만들지 않는다.
- 불확실한 정보는 가정, 확인 필요 또는 미확정 상태로 표시한다.

### 3.5 최신본과 이전 버전의 분리

- 주 작업공간에는 산출물군별 최신 검증본 한 묶음만 유지한다.
- 새 버전이 검증된 뒤에만 기존 현재본과 같은 버전의 PDF, 프리뷰, 검증기록을 이전 버전 보관함으로 이동한다.
- KPI, 예산, 역할, 일정, 과업과 실증처럼 의미가 바뀌면 관련 최신 산출물의 영향 범위를 함께 점검한다.
- 연관 산출물 전체를 먼저 검증하고, 일부가 실패하면 부분 승격하지 않는다.
- 실제 제출 완료 파일, 접수증, 서명본과 외부 증거는 자동 이동·덮어쓰기하지 않는다.

### 3.6 검증 가능한 자동화

- GUI, 승인 팝업과 특정 사용자 세션에 의존하지 않는 검사를 우선한다.
- 자동 검증 범위와 사람의 시각 확인 범위를 구분한다.
- 검증하지 못한 항목은 통과로 간주하지 않고 `대기` 또는 `확인 필요`로 기록한다.
- 테스트를 약화해 실패를 숨기지 않는다.
- 파괴적 변경보다 원본 보존, 원자 저장과 복구 가능한 절차를 우선한다.

### 3.7 독립 설치 보장

공통 정책의 기준 원본은 저장소 `shared/`에서 관리하되, 릴리즈 빌드가 각 스킬에 필요한 참조자료와 자산을 포함시킨다. 저장소 링크, 정션 또는 다른 스킬 폴더에 대한 런타임 상대경로를 설치 조건으로 삼지 않는다.

## 4. 목표 아키텍처

### 4.1 공통 코어

공통 코어는 직접 호출하는 거대 스킬이 아니라 모든 AX1 스킬이 따르는 정책과 재사용 자산의 기준 원본이다.

| 영역 | 주요 내용 | 상태 |
|---|---|---|
| 사용자 확인 | 목적·입력·범위·산출물·가정의 별도 회차 확인 | 현재 |
| 자료 판단 | 출처 우선순위, 충돌, 불확실성, 사실과 제안 분리 | 현재 |
| 문서 스타일 | 한글 원문, 제목 수준, 들여쓰기, 표와 문체 | 현재·확장 예정 |
| 산출물 생애주기 | 현재본, 이전 버전, 연동현황, 변경이력 | 현재·범용화 예정 |
| 품질 검증 | 구조, 내용, 수치, 파일 형식과 사람 확인 상태 | 현재·확장 예정 |
| 보안·개인정보 | 실제 자료 저장 금지, 익명화, 자격증명 차단 | 현재 |
| 근거 고도화 | 사례 분류, 규칙 승격·보류·충돌 관리 | 현재·범용화 예정 |

### 4.2 통합 진입점

가칭 `ax1-work`는 사용자가 세부 스킬을 몰라도 AX1 업무를 시작할 수 있게 하는 라우터다.

주요 역할은 다음과 같다.

1. 요청한 업무와 산출물 종류 식별
2. 신규 작성, 수정, 검토, 변환 또는 제출 점검 구분
3. 공식 양식과 기준 자료 존재 여부 확인
4. 필요한 질문과 결정사항 정리
5. 업무별 스킬과 문서 형식 엔진 선택
6. 산출물 버전·연동·검증 경로 안내

`ax1-work`는 전문 스킬을 대체하지 않는다. 분류가 명확하면 해당 전문 스킬로 연결하고, 적합한 스킬이 없으면 범용 작업으로 처리할지 새 모듈 후보로 기록할지 사용자와 결정한다.

### 4.3 업무별 스킬

| 스킬 또는 팩 | 역할 | 상태 |
|---|---|---|
| `bizplan-*` | 사업계획서 준비·초안·HWPX·검토·수정·제출 점검·근거 갱신 | 현재 |
| `ax1-report` | 업무보고서, 중간·결과보고서, 회의·출장 결과보고서 | 다음 |
| `ax1-proposal` | 일반 제안서, 수행계획서, 고객 요구 대응 문서 | 후보 |
| `ax1-presentation` | 보고·제안·발표 목적의 스토리보드와 편집형·이미지형 PPTX 생성 | 현재 |
| `ax1-manual` | 업무 매뉴얼, 절차서, 체크리스트 | 후보 |
| `ax1-spec` | 요구사항정의서, 기능명세서, 시험·검수 문서 | 후보 |
| `ax1-records` | 회의록, 의사결정 기록, 관리대장 | 후보 |

업무별 스킬 추가 순서는 팀 사용 빈도, 반복 시간, 오류 위험, 공통 기능 재사용률과 확보된 익명 사례를 기준으로 결정한다.

### 4.4 문서 형식 엔진

| 엔진 | 역할 | 전환 방향 |
|---|---|---|
| HWPX | 사업계획서 공식 양식 반영, AX1 일반 산출물 승인 템플릿 생성, 구조·readback 검증 | 현재 `bizplan-hwpx`의 두 호환 모드를 보존하며 향후 범용 `ax1-hwpx` 엔진 경계를 분리 |
| DOCX | Word 문서 생성, 스타일·표·페이지 렌더 검증 | 공통 문서 엔진으로 정식화 |
| PPTX | 발표자료 생성, 슬라이드 구조와 시각 검증 | 발표 스킬 도입 시 연결 |
| XLSX | 관리대장, 계산표, 추적표와 수식 검증 | 기록·관리 업무 도입 시 연결 |
| PDF | 배포·제출 후보 렌더, 페이지와 민감정보 점검 | 각 문서 엔진의 최종 검증 단계로 연결 |

문서 형식 엔진은 지원 범위와 실패 조건을 명확히 기록한다. HWPX의 자동 구조 검증처럼 사람이 사용하는 실제 프로그램에서만 확인할 수 있는 항목은 별도의 시각 검증 상태로 남긴다.

### 4.5 운영·배포 계층

| 구성 | 역할 |
|---|---|
| Git 저장소 | 공통 정책, 스킬, 익명 테스트, 문서와 배포 스크립트 관리 |
| 공유 드라이브 | 실제 프로젝트 자료, 내부 사례와 GitHub 계정이 없는 설치자를 위한 Release ZIP 관리 |
| GitHub PR | 에이전트를 활용한 익명 재현, 변경 제안, 검토와 개선 이력 관리 |
| GitHub Release | 검증된 안정 버전, ZIP, 체크섬과 주요 변경점 배포 |

## 5. 목표 저장소 구조

아래 구조는 최종 목표이며, 표시된 폴더를 한 번에 만들 필요는 없다.

```text
ax1-skills/
├─ .codex-plugin/             전체 스킬팩 메타데이터
├─ skills/
│  ├─ ax1-work/               통합 진입점과 라우팅
│  ├─ ax1-workspace/          범용 작업공간·버전·연동 관리
│  ├─ ax1-report/             범용 보고서 작성
│  ├─ ax1-hwpx/               범용 HWPX 엔진
│  ├─ ax1-docx/               범용 DOCX 엔진
│  └─ bizplan-*/              사업계획서 전문 모듈과 호환 계층
├─ shared/
│  ├─ core/                   사용자 확인·자료·버전·보안 정책
│  ├─ workflows/              작성·수정·검토·제출 흐름
│  ├─ formats/                형식별 공통 규칙
│  ├─ templates/              익명화된 공통 템플릿과 대장
│  ├─ profiles/               업무·사업 유형별 프로파일
│  ├─ evidence/               재사용 가능한 근거 레지스터
│  └─ tools/                  공통 검증 도구
├─ examples/                  익명 회귀·수용 테스트 예시
├─ scripts/                   동기화·검증·패키징 도구
├─ tests/                     공통·스킬·설치 격리 테스트
├─ docs/                      팀원·기여자·배포자 문서
└─ .changes/                  릴리즈 전 사용자 영향 변경 조각
```

현재 저장소 이름과 구조는 통합 기반이 검증될 때까지 유지한다. 저장소 이름 변경, 플러그인 ID 변경과 설치 안내 전환은 호환성 영향이 있으므로 별도 승인과 마이그레이션 계획을 거쳐야 한다.

## 6. 표준 작업 흐름

모든 산출물은 업무 특성에 맞게 다음 공통 흐름을 조합한다.

```text
요청 접수
  → 이해 내용 설명 및 사용자 확인
  → 입력자료·양식·제약·완료기준 점검
  → 질문·답변과 결정 대장으로 내용 구체화
  → 목차·양식·페이지별 내용 배분
  → 업무별 초안 또는 수정안 작성
  → 파일 형식 엔진으로 산출물 생성
  → 내용·구조·수치·레이아웃 검증
  → 관련 최신 산출물 영향 비교와 필요한 연동
  → 새 현재본 승격 및 이전 버전 보관
  → 결과·제한·사람 확인사항 보고
```

단순 조회나 검토처럼 파일을 수정하지 않는 작업은 생성·승격 단계를 생략한다. 실제 외부 제출, 공유, 전송과 게시처럼 외부 상태를 바꾸는 행위는 별도 사용자 승인 없이는 수행하지 않는다.

## 7. 기존 AX1 Bizplan의 위치

현재 배포 스킬은 7개 사업계획서 전문 스킬과 첫 범용 확장 스킬 `ax1-presentation`을 합한 8개다. 기존 사업계획서 전문 팩은 그대로 유지한다.

| 현재 스킬 | 현재 역할 | 통합 이후 방향 |
|---|---|---|
| `bizplan-prepare` | 사업계획서 작업공간 준비 | 범용 작업공간 기능을 재사용하되 기존 호출명 유지 |
| `bizplan-draft` | 대화형 사업 설계와 초안 작성 | 사업계획서 전문 작성 모듈 유지 |
| `bizplan-hwpx` | 경량 생성과 공식 HWPX 양식 반영 | 범용 HWPX 엔진을 재사용하는 호환 모듈로 단계적 전환 |
| `bizplan-review` | 평가위원 관점 검토 | 공통 검토 절차와 사업계획서 평가 렌즈 결합 |
| `bizplan-revise` | 평가·검토의견 반영 | 공통 수정·영향분석 절차와 사업계획서 규칙 결합 |
| `bizplan-preflight` | 제출 직전 최종 점검 | 공통 제출 점검과 사업계획서별 체크 결합 |
| `bizplan-evidence-update` | 근거·프로파일·테스트 고도화 | AX1 공통 근거 체계와 사업계획서 근거를 분리해 관리 |
| `ax1-presentation` | 발표 목적·청중 기반 스토리보드와 PPTX 제작 | 공통 산출물 정책을 적용하는 범용 발표자료 전문 모듈로 유지 |

기존 스킬명, 기본 요청문과 개별 설치 ZIP은 명시적인 폐기 계획이 승인되기 전까지 유지한다. 내부 구현을 공통 코어로 옮기더라도 사용자의 기존 호출 흐름은 깨지지 않아야 한다.

## 8. 단계별 로드맵

### 단계 0. 기준선 고정 — 완료

목표는 기존 기능을 통합 전환의 회귀 기준으로 보존하는 것이다.

- 7개 사업계획서 스킬의 역할과 호출 경계 유지
- 전체·개별 ZIP과 SHA-256 배포 유지
- 사용자 이해 확인 게이트 적용
- 최신본·이전 버전·산출물 연동 규칙 적용
- HWPX 경량 생성과 공식 양식 반영 경계 유지
- PR 변경 조각과 배포자 중심 버전 정책 적용

완료 기준은 기존 빌드와 기능 수용 테스트가 통과하고 현재 안정 Release로 복원할 수 있는 상태다.

### 단계 1. 통합 구조와 공통 정책 인벤토리 — 진행 중

목표는 어떤 규칙이 AX1 공통이고 어떤 규칙이 사업계획서 전용인지 명시하는 것이다.

- 공통 정책·자산·테스트 목록 작성
- 사업계획서 전용 평가 렌즈와 프로파일 표시
- 스킬별 공통 자원 의존 관계 작성
- 현재 기능과 계획 기능의 상태 표기 도입
- 향후 저장소·플러그인 명칭 후보와 전환 조건 기록

공통 정책 분류와 `ax1-work` 설계 문서는 작성됐으며, 실제 공통 기준 원본 분리와 스킬 구현은 아직 시작하지 않았다.

완료 기준은 각 공통 규칙에 기준 원본, 배포 대상 스킬과 회귀 테스트가 연결되는 것이다.

### 단계 2. AX1 공통 코어 범용화

목표는 사업계획서 표현을 제거해도 의미가 유지되는 정책을 범용 기준 원본으로 정리하는 것이다.

- 사용자 확인, 자료 우선순위, 불확실성, 보안 정책 범용화
- 산출물 버전·동기화·변경이력 정책 범용화
- 문서 스타일 프로파일을 업무별로 확장 가능한 구조로 정리
- 빌드 시 각 독립 스킬에 공통 자원이 포함되는 매핑 일반화
- 새 스킬이 공통 확인 게이트와 보안 검사를 우회하지 못하는 불변조건 추가

완료 기준은 현재 8개 스킬의 동작과 패키지가 바뀌지 않으면서 공통 정책의 중복이 줄어드는 것이다.

### 단계 3. 통합 진입점 `ax1-work` 도입

목표는 세부 스킬을 몰라도 요청 목적에 맞는 작업 경로를 선택하게 하는 것이다.

- 산출물 종류, 작업 유형, 양식과 파일 형식 분류
- 사용자 확인 후 필요한 질문만 수집
- 기존 `bizplan-*` 스킬 라우팅
- 지원하지 않는 요청의 안전한 중단과 후보 기록
- 라우팅 충돌·오호출·무한 위임 방지 테스트

완료 기준은 대표 요청 세트에서 올바른 전문 스킬을 선택하고, 전문 스킬의 확인·승인 절차를 생략하지 않는 것이다.

새로운 사용자 진입 흐름이 생기므로 기존 사용법을 유지하더라도 이 단계가 포함된 첫 배포는 마이너 버전 후보로 검토한다.

### 단계 4. 범용 작업공간과 산출물 생애주기

목표는 사업계획서에 한정된 작업공간 준비와 버전 관리를 일반 산출물에 적용하는 것이다.

- 가칭 `ax1-workspace` 도입
- 프로젝트 종류에 따른 안전한 폴더 프로파일 선택
- 신규 파일만 만드는 멱등 작업공간 생성
- 산출물군·단계·버전·관련 파일 판정
- 최신본 연동현황과 이전 버전 대장 범용화
- 모호성, 파일 잠금과 검증 실패 시 기존 현재본 유지

완료 기준은 빈 프로젝트와 기존 자료가 있는 프로젝트 모두에서 이동·삭제·덮어쓰기 없이 안전하게 동작하는 것이다.

### 단계 5. 첫 비사업계획서 모듈 `ax1-report`

목표는 통합 구조가 실제 다른 업무에도 재사용되는지 확인하는 것이다.

초기 지원 범위는 다음 세 유형으로 제한한다.

- 일반 업무보고서
- 중간·결과보고서
- 회의·출장 결과보고서

주요 기능은 목적·독자·완료기준 질문, 목차 설계, 사실·결정·성과·후속조치 구분, 양식 배분, DOCX 또는 HWPX 출력과 검증이다.

완료 기준은 익명 사례 기반 수용 테스트, 빈 영역 점검, 원문·수치 보존, 버전·연동 검증과 기존 사업계획서 회귀 테스트를 모두 통과하는 것이다.

### 단계 6. 문서 형식 엔진 경계 확정

목표는 HWPX·DOCX 같은 형식 기능을 여러 업무 스킬이 안전하게 재사용하게 하는 것이다.

- 범용 HWPX 지원 범위와 `bizplan-hwpx` 호환 경계 결정
- DOCX 스타일·렌더·페이지 검증 표준화
- 형식 엔진별 자동 검사와 사람 확인 상태 표준화
- 개별 엔진 ZIP과 전체 스킬팩 설치 격리 테스트
- 템플릿 출처·권한·SHA-256·익명화·재현 테스트 기준 통일

완료 기준은 사업계획서와 보고서가 같은 형식 엔진을 사용하면서도 업무별 내용 규칙이 섞이지 않는 것이다.

### 단계 7. 업무 모듈 점진 확장

우선순위 후보는 다음과 같다.

1. 제안서·수행계획서
2. 보고·제안 발표자료
3. 회의록·의사결정 기록·관리대장
4. 업무 매뉴얼·절차서
5. 요구사항정의서·기능명세서
6. 시험·검수·결과 문서

각 모듈은 익명 사례, 명확한 사용자 문제, 기존 스킬과 구분되는 라우팅, 재현 가능한 테스트가 준비된 뒤 추가한다. 사례 한 건의 취향을 곧바로 팀 공통 규칙으로 승격하지 않는다.

### 단계 8. AX1 통합 브랜드와 팀 표준 전환

목표는 검증된 통합 체계를 팀의 기본 설치·업데이트 경로로 전환하는 것이다.

- 저장소 이름과 플러그인 ID 변경 여부 최종 결정
- 기존 URL·설치본·스킬명 마이그레이션 안내
- 통합 README와 HTML 안내문 전환
- 모든 AX1 산출물의 개선 접수를 에이전트 기반 GitHub PR로 통일
- 배포자 검증 목록과 롤백 절차 갱신
- 팀 파일럿, 교육, 피드백과 지원 범위 확정

완료 기준은 신규 설치, 기존 설치 업데이트와 이전 안정 버전 복원이 모두 문서화·검증되는 것이다.

## 9. 릴리즈와 버전 정책

### 제품 버전

- 현재 안정 제품은 AX1 Skill Pack `v0.8.1`이다.
- 기존 흐름을 유지하는 결함 수정과 호환 개선은 패치 후보로 묶는다.
- 통합 진입점, 새 독립 스킬 또는 새 필수 의존성이 생기면 마이너 후보로 검토한다.
- 호환되지 않는 설치 경로, 스킬명 또는 저장소 ID 변경은 별도 전환 계획과 사용자 승인이 필요하다.
- 커밋이나 개선 요청마다 태그를 만들지 않고, 검증된 변경 묶음에만 버전·태그·Release를 만든다.

첫 범용 확장 스킬과 공통 기반 설계를 포함한 `0.8.0`에서 통합 스킬팩 전환을 시작했다. 통합 진입점 `ax1-work`는 아직 설계 상태이므로 구현·검증이 완료된 후 별도 마이너 후보로 판단한다. 여러 업무 모듈과 설치 체계가 팀에서 안정화된 뒤 `1.0.0`을 검토한다.

### 개별 스킬 버전

- 전체 스킬팩 버전과 각 스킬 버전을 분리한다.
- 변경되지 않은 스킬은 전체 Release가 바뀌어도 개별 버전을 불필요하게 올리지 않는다.
- 릴리즈 노트에 변경 스킬, 설치 영향, 기여자, 검증 상태와 알려진 제한을 기록한다.

### 배포 채널

- `main`: 다음 안정 배포를 준비하는 검증 가능한 통합 상태
- GitHub Release: 팀원이 설치할 공식 안정 배포
- 공유 드라이브: GitHub 계정이 없는 팀원에게 Release ZIP과 체크섬 전달
- `.changes/`: 다음 Release에 반영할 사용자 영향 변경 누적

## 10. 팀 운영 원칙

### 팀원

- 공식 안정 Release 또는 배포자가 전달한 동일 ZIP을 설치한다.
- 실제 프로젝트 자료는 접근이 통제된 프로젝트 폴더나 공유 드라이브에서 관리한다.
- 개선이 필요하면 에이전트에게 문제 상황, 기대 결과와 민감정보 없는 재현 예시를 제공하고 수정·검증·PR 생성을 요청한다.

### 기여자와 기여자 에이전트

- 최신 `main`에서 한 가지 목적의 작은 변경을 제안한다.
- 저장소 지침과 PR 운영 원칙을 먼저 읽는다.
- 실제 고객·사업·프로젝트 자료와 자격증명을 커밋하지 않는다.
- 사용자 영향 변경 조각과 재현 가능한 테스트를 포함한다.
- 버전, 태그와 GitHub Release는 수정하지 않는다.

### 배포자

- 요청과 PR을 최신 공통 정책에 맞게 통합한다.
- 기존 호출·개별 ZIP·전체 ZIP의 호환성을 확인한다.
- 개인정보·템플릿 권한·외부 의존성과 검증 증거를 점검한다.
- 보수적 버전 정책에 따라 변경을 묶고 주요 변경점이 포함된 Release를 배포한다.

9. 지원 범위, 자동 검증과 사람 확인 한계의 정직한 표시
10. 전체 ZIP과 개별 ZIP의 동일 동작

문서 형식별 추가 게이트를 적용한다.

- HWPX: ZIP CRC, XML, mimetype, 구조, readback, open-safety, 프리뷰와 한컴 시각 확인 상태
- DOCX: 패키지 무결성, 스타일, 텍스트·표 readback, 페이지 렌더와 잘림 확인
- PPTX: 슬라이드 구조, 폰트·레이아웃, 오버플로와 렌더 확인
- XLSX: 수식·참조·자료형, 오류 셀, 시트 구조와 표시 형식 확인
- PDF: 페이지 수, 텍스트·이미지 렌더, 잘림, 파일명과 민감정보 확인

## 12. 범위에서 제외하는 것

- 하나의 거대한 스킬에 모든 업무 지식을 넣는 구조
- 실제 프로젝트 원본과 생성 산출물을 Git 저장소에 보관하는 것
- 공식 양식, 수치와 의미 있는 문서 구조를 사용자 확인 없이 변경하는 것
- 검증되지 않은 AI 생성 내용을 최종 제출본으로 자동 승격하는 것
- 사용자의 별도 승인 없이 외부 제출·전송·게시하는 것
- 특정 프로젝트 사례 하나를 모든 AX1 업무의 공통 규칙으로 즉시 적용하는 것
- GUI 자동화 성공만으로 구조·내용 검증을 대체하는 것
