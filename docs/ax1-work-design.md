# `ax1-work` 통합 진입 스킬 설계

`ax1-work`는 AX1팀 산출물 요청의 목적, 작업 유형, 준비도와 파일 형식을 분류해 적절한 전문 스킬로 연결하는 통합 진입점이다. 직접 모든 산출물을 작성하는 거대 스킬이 아니며, 전문 스킬의 판단·편집·검증 절차를 복제하지 않는다.

이 문서는 구현 전 설계다. 현재 저장소에는 아직 `skills/ax1-work/`가 없으며 설치·호출할 수 없다.

## 1. 설계 목표

- 사용자가 세부 스킬 이름을 몰라도 `AX1 스킬로 … 해줘`라고 요청할 수 있게 한다.
- 작업을 시작하기 전에 이해한 목적·입력·범위·산출물·가정을 사용자와 확인한다.
- 하나의 주 전문 스킬과 필요한 보조 스킬만 선택한다.
- 내용 작성, 파일 형식 처리, 검토와 제출 점검의 경계를 보존한다.
- 아직 구현되지 않은 스킬이나 지원 범위를 존재하는 것처럼 말하지 않는다.
- 직접 특정 스킬을 요청한 사용자의 선택을 불필요하게 가로채지 않는다.
- 위임 과정에서 파일 수정, 외부 전송 또는 제출 권한을 확대하지 않는다.

## 2. 비목표

`ax1-work`는 다음 작업을 직접 수행하지 않는다.

- 사업 아이디어와 구현 브리프의 상세 설계
- 사업계획서 본문 작성·평가·수정
- HWPX·DOCX·PPTX·XLSX 내부 편집
- 산출물 버전 이동과 연동 트랜잭션 실행
- 근거 레지스터와 프로파일 갱신
- Git 커밋·푸시·릴리즈
- 외부 제출·게시·메일·메시지 전송

라우팅 뒤 전문 스킬이 해당 작업을 수행한다. 설치된 적합한 전문 스킬이 없으면 `미지원` 또는 `범용 도구 사용 제안` 상태로 멈추고 사용자의 선택을 받는다.

## 3. 이름과 발견 정책

### 권장 이름

```yaml
name: ax1-work
```

짧고 행동 중심이며 사업계획서·보고서·문서 형식 어느 하나에 한정되지 않는다.

### 설명 초안

```yaml
description: AX1팀 산출물 요청의 업무 목적, 작업 유형, 준비도와 파일 형식을 분류해 설치된 AX1 전문 스킬로 연결한다. 사용자가 AX1 통합 작업을 요청하거나 어느 스킬을 써야 할지 불명확할 때 사용한다. 특정 전문 스킬을 명시했거나 일반 질의·코딩 작업에는 사용하지 않는다.
```

자동 발견은 허용하되 설명을 넓은 만능 업무 스킬처럼 쓰지 않는다. `AX1`, 팀 산출물, 여러 단계 작업 또는 스킬 선택이 불명확한 요청이 핵심 트리거다.

## 4. 호출 조건

### 사용

- `AX1 스킬로 결과보고서를 준비해줘`
- `이 자료로 어떤 AX1 스킬을 써야 해?`
- `프로젝트 폴더부터 만들고 초안·검토·제출본까지 진행하고 싶어`
- `사업계획서와 발표자료를 최신 내용으로 맞춰줘`
- 산출물 종류·작업 단계·파일 형식이 섞여 주 스킬을 바로 고르기 어려운 요청

### 직접 호출하지 않음

- 사용자가 `$bizplan-draft`, `$bizplan-hwpx`처럼 전문 스킬을 명시
- `사업계획서 제출 전 점검해줘`처럼 기존 전문 스킬이 명확히 대응
- 산출물과 관련 없는 일반 질문·코딩·검색·앱 조작
- 단순 대화나 아이디어 브레인스토밍으로 AX1 산출물 작업 의도가 없음

전문 스킬이 명확해도 사용자가 명시적으로 `AX1 통합 스킬로` 요청하면 `ax1-work`가 확인과 라우팅을 수행할 수 있다.

## 5. 입력 분류 모델

라우팅에는 다음 축을 사용한다. 모든 축을 사용자에게 표 형태로 보여줄 필요는 없으며, 결정에 필요한 정보만 질문한다.

### 5.1 업무 분야 `domain`

| 값 | 의미 | 현재 지원 |
|---|---|---|
| `bizplan` | 국가 R&D·공모 사업계획서와 연관 산출물 | 지원 |
| `report` | 업무·중간·결과·회의·출장 보고서 | 계획 |
| `proposal` | 일반 제안서·수행계획서 | 계획 |
| `presentation` | 보고·제안·발표 슬라이드 | `ax1-presentation` 지원 |
| `manual` | 업무 매뉴얼·절차서 | 계획 |
| `spec` | 요구사항·기능·시험·검수 명세 | 계획 |
| `records` | 회의록·의사결정 기록·관리대장 | 계획 |
| `unknown` | 자료 확인 또는 사용자 결정 필요 | 미확정 |

### 5.2 작업 유형 `action`

| 값 | 의미 |
|---|---|
| `prepare` | 작업공간과 준비현황 구축 |
| `draft` | 신규 내용·초안 작성 |
| `format` | 확정 내용을 특정 파일 형식에 반영 |
| `review` | 읽기 전용 진단과 개선안 |
| `revise` | 검토의견·요구사항을 기존 산출물에 반영 |
| `preflight` | 제출·배포 직전 최종 점검 |
| `sync` | 의미 변경을 다른 최신 산출물에 연동 |
| `evidence-update` | 사례·근거를 스킬 정책과 테스트에 반영 |
| `unknown` | 요청을 더 구체화해야 함 |

### 5.3 산출물 `artifact`

- 텍스트 문안
- 작업공간
- DOCX
- HWPX
- PPTX
- XLSX
- PDF
- 복합 산출물

파일 형식은 업무 목적을 대신하지 않는다. `HWPX로 사업계획서를 작성`은 내용이 확정되지 않았으면 먼저 `bizplan-draft`, 확정 뒤 공식 양식을 사용하는 `bizplan-hwpx` 순서다. 내용이 확정된 일반 HWPX 산출물은 `bizplan-hwpx`의 승인 AX1 산출물 템플릿 경로를 사용한다.

### 5.4 준비도 `readiness`

| 값 | 의미 |
|---|---|
| `idea` | 목적과 구현 방식이 아직 아이디어 수준 |
| `brief-ready` | 핵심 결정과 구현 브리프가 확정됨 |
| `content-ready` | 파일에 넣을 문안·표·값이 확정됨 |
| `artifact-ready` | 검토할 문서 파일이 존재함 |
| `submission-candidate` | 제출 후보와 필수 증거가 준비됨 |
| `unknown` | 확인 필요 |

### 5.5 부작용 수준 `effect`

| 값 | 의미 | 기본 처리 |
|---|---|---|
| `read-only` | 조회·검토·진단 | 파일 수정 금지 |
| `local-write` | 프로젝트 내부 생성·수정 | 확인된 범위 안에서 전문 스킬 수행 |
| `destructive` | 덮어쓰기·삭제·대규모 이동 | 별도 승인 필요 |
| `external-write` | 제출·전송·게시·Git push·Release | 실행 직전 별도 승인 필요 |

## 6. 사용자 이해 확인과 전달

### 6.1 최초 확인

`ax1-work`는 다른 모든 절차보다 먼저 AX1 공통 사용자 확인 정책을 적용한다. 최초 응답에서는 대화에 이미 드러난 정보만 사용하고 파일·저장소·도구를 먼저 조회하지 않는다.

이 단계에서 요청이 명확하면 도구 없는 사전 분류로 업무 목적과 예상 전문 스킬을 추론해 확인문에 포함한다. 문서 목적이 결과를 바꾸지만 대화만으로 구분할 수 없을 때만 선택지를 묻는다. `ax1-work`는 전체 AX1 요청의 최상위 목적·전문 스킬 선택을 소유한다. `bizplan-hwpx`가 직접 호출되면 HWPX 안의 `사업계획서 작성`과 `일반 산출물 작성` 목적도 정하지만, `ax1-work`에서 위임받으면 확인 완료 envelope의 목적을 검증·소비하고 실제 자료에 맞는 양식·엔진만 선택한다. 자료가 envelope와 충돌할 때만 변경된 이해를 다시 확인한다.

최소 확인 내용은 다음이다.

1. 이해한 업무 목적과 산출물
2. 사용할 것으로 예상하는 입력·기준 자료
3. 진행할 범위와 제외 범위
4. 예상 전문 스킬과 파일 형식
5. 주요 가정, 위험과 후속 승인 지점

사용자가 별도 메시지로 동의한 뒤에만 자료 탐색과 실제 분류를 진행한다.

### 6.2 확인 전달 정보

구현 시 가칭 `confirmation envelope`를 같은 요청의 전문 스킬에 전달한다.

```yaml
schemaVersion: ax1.confirmation/v1
purpose: 사용자와 확인한 목적
# 아래 두 필드는 HWPX 요청일 때만 포함
documentPurpose: business-plan | general-deliverable
expectedFormatAuthority: official-rfp-form | customer-required-form | approved-ax1-template | unknown | not-applicable
inputs: 예상 입력과 기준
scope: 진행 범위
exclusions: 진행하지 않을 범위
outputs: 예상 산출물
assumptions: 주요 가정
effect: read-only | local-write | destructive | external-write
confirmedInSeparateTurn: true
```

다음 조건을 모두 만족하면 전문 스킬은 같은 최초 확인을 반복하지 않을 수 있다.

- 동일한 사용자 요청과 같은 논리적 작업 흐름
- 목적·입력·범위·제외·산출물·부작용 수준이 일치
- HWPX 요청이면 `documentPurpose`와 예상 양식 권한이 일치하며, 실제 자료 확인으로 권한이 달라지지 않음
- 사용자가 확인 뒤 새로운 범위 변경을 요청하지 않음
- 전문 스킬의 추가 작업이 확인 범위 안에 있음

하나라도 달라지면 변경된 이해 내용을 설명하고 다시 확인한다.

### 6.3 후속 승인

확인 전달은 다음 승인을 대신하지 않는다.

- 사업계획서 구현 브리프와 양식 배분 진행 승인
- HWPX dry-run 뒤 실제 반영과 시각 검증
- 파일 덮어쓰기·삭제·이동
- 커밋·푸시·릴리즈
- 외부 제출·공유·전송
- 승인되지 않은 수치·기관 역할·대외 문구 확정

## 7. 라우팅 절차

### 7.1 확인 뒤 자료 탐색

- 현재 대화와 확인된 작업 범위에서 접근 가능한 파일만 찾음
- 이미 제공된 자료를 다시 요청하지 않음
- 자료명·버전·파일 형식과 최신 후보를 확인함
- 읽기 전용 요청이면 이 단계에서도 파일을 만들거나 이동하지 않음

### 7.2 분류

최초 확인에서 대화만으로 사전 분류한 `domain`, `action`, `artifact`, `readiness`, `effect`를 실제 자료로 정교화하고, HWPX 요청이면 `documentPurpose`와 `expectedFormatAuthority`도 정교화한다. 선택에 따라 결과가 실질적으로 달라지는 정보가 없을 때만 짧게 질문한다. 자료가 사전 분류와 충돌해 목적·양식 권한이 달라지면 조용히 전환하지 않고 변경된 이해 내용을 다시 확인한다.

### 7.3 주 스킬 선택

- 한 시점에는 한 개의 `primarySkill`을 선택한다.
- 파일 형식보다 업무 목적과 준비도를 먼저 본다.
- 보조 스킬은 실제 다음 단계에 필요할 때만 `supportingSkills`에 둔다.
- 계획 상태 스킬을 설치된 스킬처럼 선택하지 않는다.

### 7.4 실행 또는 중단

- 주 스킬이 있고 확인 범위가 일치하면 전문 절차로 진행
- 모듈이 없으면 지원하지 않는 범위와 가능한 안전한 대안을 설명
- 사용자 결정이 필요하면 2~3개 대안과 추천안을 제시하고 답변을 기다림
- 도구·의존성이 없으면 설치를 임의 실행하지 않고 필요성과 대안을 보고

## 8. 현재 스킬 라우팅 표

| 사용자 목적·상태 | 주 스킬 | 보조·후속 스킬 | 비고 |
|---|---|---|---|
| 사업계획서 작업공간 준비 | `bizplan-prepare` | 없음 | 내용 작성은 별도 요청 |
| 사업 아이디어·전체 초안·빈 양식 | `bizplan-draft` | 내용 확정 후 `bizplan-hwpx` 가능 | 질문·구현 브리프 게이트 적용 |
| 확정 사업계획서 문안의 HWPX 반영 | `bizplan-hwpx` | 제출 후보면 `bizplan-preflight` | 내용 미확정이면 draft 우선 |
| 확정 일반 산출물의 HWPX 작성 | `bizplan-hwpx` | 내용 작성 모듈 또는 범용 문서 도구 | 승인 AX1 산출물 템플릿 사용, 계약·고객 양식은 upstream 경로 |
| 사업계획서 사전 평가·진단 | `bizplan-review` | 수정 요청 시 `bizplan-revise` | 기본 읽기 전용 |
| 검토·평가의견 반영 | `bizplan-revise` | 기준본이 HWPX면 `bizplan-hwpx` | 영향 산출물 연동 포함 가능 |
| 제출 직전 최종 점검 | `bizplan-preflight` | HWPX 검증 기록은 `bizplan-hwpx` 결과 확인 | 기본 읽기 전용 |
| 새 평가자료로 스킬 고도화 | `bizplan-evidence-update` | 저장소 변경은 운영 정책 적용 | 개별 문서 작성 아님 |
| 보고·제안·사업 발표자료 제작 | `ax1-presentation` | 기준 사업계획서가 바뀌면 관련 전문 스킬과 연동 | 스토리보드·모드·이미지형 샘플 게이트 적용 |
| 최신 사업계획서와 발표자료 내용 연동 | 의미 변경의 주 전문 스킬 | 형식별 스킬·도구 | 독립 `sync` 스킬은 아직 없음 |

## 9. 순차 라우팅 예시

### 9.1 아이디어에서 HWPX 사업계획서까지

```text
ax1-work
  → bizplan-draft: 질문·구현 브리프·양식 배분·내용 확정
  → bizplan-hwpx: 확정 내용의 양식 반영·구조·readback·시각 검증
  → bizplan-preflight: 제출 후보 최종 점검
```

세 스킬을 처음부터 한 번에 실행하지 않는다. 각 단계 완료 기준과 후속 승인을 충족한 뒤 다음 단계로 간다.

### 9.2 검토의견 반영

```text
ax1-work
  → bizplan-revise: 의견 분해·수정문안·영향 위치 확정
  → bizplan-hwpx 또는 DOCX 절차: 실제 파일 반영
  → 관련 최신 산출물 후보 검증·연동
  → bizplan-preflight: 제출 후보 재점검
```

### 9.3 읽기 전용 검토

```text
ax1-work
  → bizplan-review
  → 문제 위치·근거·수정전략 보고
```

사용자가 수정까지 요청하지 않으면 revise·파일 편집·버전 전환으로 넘어가지 않는다.

## 10. 미래 스킬 라우팅

| 요청 | 계획 라우팅 | 현재 처리 |
|---|---|---|
| 일반 업무·중간·결과보고서 | `ax1-report` | 미구현이라고 밝히고 설치된 일반 문서 도구 사용 여부를 사용자와 결정 |
| 범용 작업공간 준비 | `ax1-workspace` | 사업계획서면 `bizplan-prepare`, 그 외는 안전한 수동 설계 또는 대기 |
| 범용 HWPX 문서 | `ax1-hwpx` | 현재는 `bizplan-hwpx`의 승인 AX1 산출물 템플릿 호환 모드 사용, 향후 범용 엔진 분리 |
| 일반 제안서 | `ax1-proposal` | 미구현, 임의로 사업계획서 규칙 적용 금지 |
| 발표자료 | `ax1-presentation` | 지원, 편집 가능한 네이티브 모드를 우선하고 이미지형은 편집 불가 확인 후 사용 |
| 매뉴얼·명세·기록 | 각 전문 모듈 | 미구현, 적합한 범용 도구와 완료 기준을 별도 확인 |

계획 스킬의 이름만 반환하고 작업이 가능한 것처럼 진행하지 않는다. 플랫폼에 일반 문서·프레젠테이션·스프레드시트 스킬이 설치돼 있어도 그것이 AX1 검증·버전 정책을 자동으로 포함한다고 가정하지 않는다.

## 11. 라우팅 충돌 해결

다음 우선순위를 사용한다.

1. 사용자가 명시한 전문 스킬
2. 사용자가 명시한 업무 목적과 작업 유형
3. 내용 준비도
4. 기준 자료와 공식 양식
5. 원하는 파일 형식

예시:

- `HWPX로 사업계획서 초안 작성` + 내용 미확정 → `bizplan-draft`가 주 스킬, `bizplan-hwpx`는 후속
- `작성된 계획서 평가해줘` → `bizplan-review`, 파일이 HWPX라는 이유로 `bizplan-hwpx`를 주 스킬로 선택하지 않음
- `평가의견 반영 여부만 확인` → `bizplan-review`, 실제 수정 요청이 있어야 `bizplan-revise`
- `제출 직전 오탈자도 고쳐줘` → 먼저 `bizplan-preflight`로 범위를 확인하고, 실제 수정은 별도 확인된 최소 범위로 수행
- `$bizplan-hwpx로 이 파일 수정` → `ax1-work`가 사용자 선택을 가로채지 않음

두 스킬이 동시에 주 스킬처럼 보이면 한 번에 병합하지 않고 현재 완료 기준을 먼저 충족해야 하는 스킬을 선택한다.

## 12. 라우팅 결정 기록

복잡한 다단계 요청은 다음 정보를 메모리상 유지한다.

```yaml
schemaVersion: ax1.route-decision/v1
requestSummary: 요청 요약
domain: bizplan
action: draft
artifact: [text, hwpx]
readiness: idea
effect: local-write
primarySkill: bizplan-draft
supportingSkills: [bizplan-hwpx, bizplan-preflight]
status: routed
reason: 내용이 미확정이므로 형식 반영 전에 구현 브리프가 필요함
nextGate: 구현 브리프 방향 확인
```

허용 상태는 다음과 같다.

- `routed`: 현재 주 스킬이 결정됨
- `needs-user-decision`: 선택에 따라 결과가 달라짐
- `unsupported`: 설치된 AX1 전문 스킬이 없음
- `blocked`: 자료·도구·권한·형식 문제로 시작 불가

일반 요청마다 별도 라우팅 파일을 만들지 않는다. 여러 단계·여러 산출물 프로젝트에서 사용자가 추적 문서를 요청했을 때만 프로젝트 내부에 최소 정보를 저장한다.

## 13. 전문 스킬 전달 계약

전달 시 다음을 보존한다.

- 원래 사용자 요청
- 확인된 목적·입력·범위·제외·산출물·가정
- HWPX 요청이면 확인된 `documentPurpose`와 예상 양식 권한
- `domain`, `action`, `artifact`, `readiness`, `effect`
- 선택한 기준 자료와 확인하지 못한 자료
- 주 스킬 선택 이유
- 다음 완료 기준과 후속 승인

전문 스킬은 전달 내용을 사실로 무조건 신뢰하지 않고 실제 자료를 확인한다. 분류가 잘못됐거나 범위가 달라지면 조용히 다른 작업으로 전환하지 않고 사용자에게 변경된 이해를 설명한다.

## 14. 오류·미지원·의존성 처리

### 모호한 요청

결과를 바꾸는 핵심 선택만 질문한다. 사용자가 답을 모르겠다고 하면 2~3개 대안, 차이와 추천 기본값을 제시한다.

### 미지원 요청

- 어떤 AX1 모듈이 없는지 명확히 설명
- 현재 가능한 범용 작업과 AX1 정책 적용 한계를 구분
- 새 스킬 후보로 기록할지 사용자에게 제안
- 없는 스킬의 출력·검증을 완료했다고 표현하지 않음

### 의존성 부족

- 설치된 도구와 필요한 도구를 구분
- 설치·업데이트는 사용자 요청과 권한이 있을 때만 수행
- GUI·외부 서비스가 필요한 경우 자동 검증과 사람 확인 범위를 설명
- 대체 형식이나 텍스트 문안으로 안전하게 진행할 수 있으면 제안

### 외부 상태 변경

Git push, Release, 제출, 게시와 메시지 전송은 라우팅 결과만으로 실행하지 않는다. 실행 대상·범위·영향을 설명하고 해당 작업의 별도 승인 절차를 따른다.

## 15. 권장 스킬 폴더 구조

`skill-creator`의 점진적 공개 원칙에 따라 진입 파일은 짧게 유지한다.

```text
skills/ax1-work/
├─ SKILL.md
├─ agents/
│  └─ openai.yaml
└─ references/
   ├─ 01-routing-matrix.md
   ├─ 02-confirmation-and-handoff.md
   └─ 03-acceptance-scenarios.md
```

초기 버전에는 `scripts/`와 `assets/`를 만들지 않는다. 라우팅은 요청 의미와 설치 상태를 판단하는 작업이므로 결정적 변환 스크립트의 이점이 아직 없다. 반복되는 기계 판독용 라우팅 레지스트리가 필요하다는 실제 사례가 쌓일 때만 추가한다.

### `SKILL.md`에 둘 내용

- 목적과 호출·제외 조건
- 사용자 확인 우선
- 분류 축과 주 스킬 선택 원칙
- 전문 스킬 전달·권한 경계
- 세 참조자료를 읽을 조건
- 미지원·범위 변경 처리

### 참조자료에 둘 내용

- `01-routing-matrix.md`: 현재·계획 스킬과 충돌 규칙
- `02-confirmation-and-handoff.md`: confirmation envelope와 후속 승인
- `03-acceptance-scenarios.md`: 현실적인 요청·기대 라우팅·금지 동작

전문 스킬의 상세 절차를 복사하지 않고 해당 스킬 자체를 기준으로 사용한다.

## 16. UI 메타데이터 방향

자동 호출을 허용하되 설명과 기본 프롬프트를 통합 업무에 한정한다.

```yaml
interface:
  display_name: AX1 Work
  short_description: AX1 산출물 요청을 적합한 전문 스킬로 연결
  default_prompt: AX1 통합 스킬로 이 업무의 목적과 산출물을 확인하고 적합한 작업 경로를 선택해줘.
```

최종 키 이름과 생성 방식은 구현 시 현재 Codex 스킬 메타데이터 규격을 확인한다. 명시적 호출 전용 정책은 사용자가 요청하지 않았으므로 기본 자동 발견을 유지한다.

## 17. 수용 테스트 설계

| ID | 요청 | 기대 결과 | 금지 동작 |
|---|---|---|---|
| `R01` | `AX1 스킬로 사업계획서 초안을 작성해줘` | 확인 후 `bizplan-draft` | 확인 전 파일 조회, 바로 전체 초안 |
| `R02` | `아이디어는 없고 HWPX 양식만 있어. 채워줘` | 내용 미확정 판정, draft 선행 | 빈칸부터 임의 작성 |
| `R03` | `확정 문안을 이 HWPX에 넣어줘` | `bizplan-hwpx` | 사업 아이디어 인터뷰 강제 |
| `R04` | `계획서를 평가해줘` | `bizplan-review`, 읽기 전용 | 원문 자동 수정 |
| `R05` | `검토의견을 반영해 수정본을 만들어줘` | `bizplan-revise`, 형식에 따라 후속 엔진 | 의견 확인만 하고 완료 주장 |
| `R06` | `내일 제출할 파일 최종점검해줘` | `bizplan-preflight` | 대규모 신규 내용 생성 |
| `R07` | `$bizplan-hwpx로 수정해줘` | 명시한 전문 스킬 존중 | ax1-work로 불필요하게 재라우팅 |
| `R08` | `AX1 스킬로 일반 결과보고서를 만들어줘` | `ax1-report` 미구현 고지와 안전한 선택지 | 계획 스킬이 있다고 주장 |
| `R09` | `보고서 검토만 해줘` | read-only 유지 | 수정본·버전 대장 생성 |
| `R10` | `공식 HWPX 양식으로 사업계획서를 작성해줘` | `bizplan-draft` 후 공식 양식 `bizplan-hwpx` | AX1 일반 산출물 템플릿으로 대체 |
| `R11` | `확정된 정의서를 AX1 HWPX 양식으로 만들어줘` | `bizplan-hwpx` 경량 산출물 모드 | 임의 템플릿·저장소 정션 의존 |
| `R12` | `검토 끝나면 담당기관에 제출해줘` | 검토와 외부 제출 승인 분리 | 라우팅 확인만으로 제출 |
| `R13` | 확인 후 사용자가 산출물을 변경 | 변경된 이해 재확인 | 이전 확인을 다른 범위에 재사용 |
| `R14` | KPI 표의 띄어쓰기만 수정 | 형식 변경, 종속 프리뷰만 재생성 | 다른 산출물 내용 버전 전파 |
| `R15` | `이 자료로 HWPX 문서를 만들어줘` | 파일을 열기 전 사업계획서/일반 산출물 두 목적 중 선택 요청 | 첨부 선조회, 임의 AX1 템플릿 선택 |
| `R16` | `고객 지정 양식으로 결과보고서를 작성해줘` | 일반 산출물 + 고객 필수 양식 권한 | 승인 AX1 템플릿으로 대체 |
| `R17` | `사업계획서인데 자유양식이야` | 사업계획서 목적 유지, 확인 뒤 공고 지침 검토 | 일반 AX1 템플릿으로 자동 전환 |
| `R18` | 동일 confirmation envelope로 `bizplan-hwpx` 위임 | 최초 확인을 반복하지 않고 HWPX 세부 절차 진행 | 같은 목적·범위의 중복 확인 |

테스트는 설명 문구의 정확한 문자열만 비교하지 않는다. 어떤 스킬을 선택했는지, 확인 전에 도구를 호출했는지, 파일을 수정했는지와 같은 관찰 가능한 행동을 검증한다.

## 18. 구현 순서

1. AX1 공통 정책의 최소 `C0` 기준 원본 확정
2. confirmation envelope의 재사용·재확인 조건을 현재 8개 스킬과 합의
3. `skills/ax1-work/`와 세 참조자료 작성
4. 빌드의 스킬 목록·확인 게이트·개별 ZIP 불변조건에 추가
5. 현재 8개 스킬 라우팅 수용 테스트 작성
6. 미지원·직접 전문 스킬 호출·외부 상태 변경 테스트
7. 전체·개별 ZIP 설치 격리 검증
8. 팀 파일럿 뒤 설명과 충돌 규칙만 좁게 보완

## 19. 릴리즈 영향

`ax1-work`는 새 독립 스킬이자 새로운 사용자 진입 흐름이므로 구현·검증이 완료된 첫 배포는 마이너 버전 후보다. 현재 문서 설계만으로 버전, 플러그인 ID, 설치 안내, 태그 또는 Release를 변경하지 않는다.

기존 7개 `bizplan-*`와 `ax1-presentation` 스킬명과 직접 호출은 유지한다. 통합 진입점은 새로운 선택지이며 기존 사용법의 강제 대체가 아니다.

## 20. 구현 완료 기준

- 짧고 구분력 있는 name·description
- 확인 전 도구 호출 금지와 확인 전달 테스트 통과
- 현재 8개 전문 스킬의 올바른 라우팅
- 직접 전문 스킬 호출 비개입
- 미구현 스킬을 지원한다고 주장하지 않음
- 한 개의 주 스킬과 필요한 보조 스킬만 선택
- 읽기·쓰기·파괴적·외부 작업 권한 경계 유지
- 전체·개별 ZIP에서 동일 동작
- 기존 사업계획서 호출·패키징 회귀 없음

이 설계를 승인한 뒤 실제 스킬 구현은 별도 사용자 확인과 변경 작업으로 진행한다.
