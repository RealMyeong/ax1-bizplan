# AX1 개선 제안·PR 운영 원칙

GitHub Discussion·Issue·Pull Request를 AX1 Skill Pack의 공식 개선 제안·추적·구현 검토 채널로 사용함. Google Form은 사용하지 않으며 에이전트가 제안의 성숙도를 판단해 적절한 채널을 선택함

## 역할

| 역할 | 책임 |
|---|---|
| 기여자 | 아이디어·문제 공유, Fork의 로컬 개선, 범위가 작은 PR, 변경 조각과 근거 제출 |
| 기여자 에이전트 | 채널 선택 설명, 저장소 지침 확인, 개인정보·버전 파일 차단, Fork·테스트·PR 양식 작성 |
| 배포자 | 최신 `main` 기준 통합, 공통 정책 동기화, 회귀 검증, 버전 결정, 릴리즈 |

PR은 완성된 배포본이 아니라 통합할 기능 제안임. PR이 생성된 뒤 `main`이 바뀌어도 실패로 보지 않으며, 배포자가 최신 `main`에서 통합 브랜치를 만들어 필요한 커밋을 이식하거나 기여자에게 갱신을 요청함

## Discussion·Issue·PR 선택 기준

| 채널 | 선택 조건 | 결과 |
|---|---|---|
| Discussion | 해결 방향·범위·대안이 열려 있고 관리자·팀 의견이 먼저 필요함 | 목표, 선택지, 기대효과와 결정할 질문을 토론함 |
| Issue | 재현 가능한 문제나 요구사항과 완료조건은 있으나 구현·검증이 아직 없음 | 담당·우선순위·결정사항과 구현 진행을 추적함 |
| Pull Request | 구현 결정이 끝나고 한 가지 목적의 수정·테스트·변경 조각이 준비됨 | 병합 가능한 변경을 검토함 |

에이전트는 외부 등록 전에 선택한 채널과 이유를 사용자에게 설명함. Discussion 기능을 사용할 수 없으면 Issue로 전환하고 `논의 필요`와 관리자가 결정해야 할 질문을 남김. 인증·권한이 없으면 중단하고 필요한 계정 또는 권한을 안내함

```text
아이디어 제안
→ Discussion 또는 Issue 등록
→ 프로젝트 관리자와 방향 협의
→ 구현 결정
→ 코드·문서 수정 및 커밋
→ PR 제출
```

## 주간 운영 주기

1. 팀원과 팀원 에이전트는 개선사항이 생길 때마다 Discussion·Issue·PR 중 적절한 제안을 수시로 등록함
2. 배포자는 매주 일요일까지 Discussion·Issue의 구현 결정과 접수된 PR을 분류하고 최신 `main`에서 안전한 기능을 취합·통합함
3. 통합 ZIP과 CI 내부 개별 스킬 ZIP 격리 검사 및 관련 수용 테스트를 통과한 변경은 월요일 새 Release로 배포함
4. 실패·추가정보 필요·보류 변경은 억지로 포함하지 않고 다음 주기로 이월하며 PR에 상태와 이유를 남김
5. 검증 완료 변경이 없으면 빈 Release를 만들지 않음. 업무 중단 수준의 결함은 주간 주기를 기다리지 않고 별도 패치할 수 있음

릴리즈 노트에는 각 반영 PR의 번호, 기여자가 선택한 표시명 또는 GitHub 계정, 실제 반영 내용, 제외·보류 범위와 검증 상태를 포함함. 공동 아이디어를 하나의 통합 커밋으로 재구성해도 기여 출처를 빠뜨리지 않음

## Fork 기반 에이전트 제출 흐름

```text
원본 저장소
  ↓ Fork
내 GitHub 저장소
  ↓ Clone
로컬 저장소
  ↓ 작업·Commit·Push
내 GitHub 저장소의 작업 브랜치
  ↓ Pull Request
원본 저장소
```

1. 원본 `RealMyeong/ax1-bizplan`을 기여자의 GitHub 계정으로 Fork함
2. 기여자의 Fork를 Clone하고 이를 `origin`, 원본 저장소를 `upstream`으로 확인·등록함
3. `AGENTS.md`, `CONTRIBUTING.md`와 이 문서를 읽고 최신 `upstream/main`에서 `contrib/<짧은-주제>` 브랜치를 준비함
4. 재현 요청문·실제 동작·기대 동작을 민감정보 없는 예시로 정리함
5. 한 가지 목적의 수정, 직접 테스트, 전체 빌드와 `.changes` 변경 조각을 완료함
6. 버전·릴리즈 파일과 실제 사업자료가 포함되지 않았는지 확인함
7. 기여자의 Fork 작업 브랜치에 커밋·Push하고 원본 저장소 `main`을 대상으로 PR을 생성함
8. PR URL, 원격 구성, 검증 결과와 미검증 항목을 사용자에게 보고함

Fork의 `main`에는 작업 커밋을 쌓지 않고 원본 `main` 동기화용으로 유지함. 원본 저장소 직접 Push 권한이 있는 관리자는 내부 브랜치를 사용할 수 있지만, 일반 팀원의 기본 경로는 Fork임. GitHub 인증이나 Fork 권한이 없으면 에이전트는 중단하고 필요한 계정·권한을 알려줌

## PR 허용 기준

- 사용자 문제와 기대 결과가 명확함
- 한 PR에서 한 기능 또는 한 결함만 다룸
- 기존 스킬과 중복될 때 새 스킬보다 기존 스킬의 모드·참조·스크립트로 통합하는 방안을 먼저 검토함
- 새 스킬은 독립 라우팅이 필요한 경우에만 제안하며 모든 공통 정책·패키징·설치 문서를 함께 갱신함
- 표준 라이브러리·headless 구현은 장점으로 인정하되 지원 범위와 실패 조건을 명시함
- 사용자 확인 없이 의미 기호·사업 수치·기관명·문서 구조를 바꾸지 않음
- HWPX 변경은 사업계획서 공식 양식 경로와 AX1 일반 산출물 양식 경로를 구분하고, 공식 양식을 팀 템플릿으로 대체하지 않음

## 병합 전 배포자 점검

1. PR 작성자의 커밋과 기여 표기를 보존할 방법 확인
2. 최신 `main`의 확인 게이트, 산출물 버전·연동 정책, 팀 안내와 HTML 안내문 적용
3. 공개 통합 ZIP과 CI 내부 개별 스킬 ZIP 격리 환경에서 자산·스크립트가 같은 경로로 동작하는지 확인
4. Windows와 CI 환경에서 외부 창·승인 팝업 없이 자동 검증 가능한지 확인
5. 실제 문서·개인정보·회사 내부 표본·자격증명·배포 권한 불명 자산 확인
6. 전체 빌드, 설치 격리 테스트, 기능 수용 테스트 수행
7. 보수적 버전 정책으로 배포자가 버전과 릴리즈 노트를 결정

## 버전 책임

기여자는 버전을 올리지 않음. 배포자가 통합 결과를 보고 결정함

- 기존 사용 흐름을 유지하는 호환 개선·결함 수정: 패치 후보
- 새 독립 스킬 또는 새 사용자 흐름: 마이너 후보
- 기존 사용법과 호환되지 않는 변경: 별도 전환 계획과 사용자 승인 필요

릴리즈 노트에는 주요 변경점, 설치·업데이트 영향, 기여자, 알려진 제한과 검증 상태를 기록함
