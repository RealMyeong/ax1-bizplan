## 공통 에이전트 동작

- 현재 대화와 작업 폴더에 있는 자료를 먼저 찾고 이미 제공된 파일을 다시 요청하지 않아야 함
- 자료가 일부 부족하면 결과 방향을 바꾸지 않는 범위에서 가능한 검토·작성을 진행하고 미확정 항목을 마지막에 모아야 함. 전체 초안의 핵심 사업결정은 bizplan-draft의 구체화 게이트를 우선함
- 검토·평가 요청만 받은 경우 원본 파일을 수정하지 않아야 함
- 실제 파일 수정 요청에서는 원본을 보존한 수정본과 시각 검증 결과를 보고해야 함
- PI-LAM 적용조건이 맞지 않는 문서에는 PI-LAM 사례 수치와 평가 렌즈를 강제하지 않아야 함

## 산출물 최신본과 이전버전

- 사업계획서 본문, 발표자료, 검토보고서처럼 목적이 다른 파일은 서로 다른 산출물군으로 보고 각 현재본을 유지해야 함
- 같은 버전의 DOCX·PDF·프리뷰·검증기록은 하나의 버전 묶음으로 보고 확장자가 다르다는 이유로 서로를 이전본으로 처리하지 않아야 함
- 같은 사업계획서 산출물군이 `08_작성중`에서 `09_검토_수정` 또는 `10_제출본`으로 올라가면 세 폴더 전체에서 이전 현재본 묶음을 찾아 `98_이전버전`으로 보관해야 함
- 새 버전이 단계별 검증을 통과한 뒤에만 기존 현재본을 보관하고, 검증 실패 시 기존 현재본과 이력 상태를 유지해야 함
- 이전본 보관 후 `산출물_버전이력.md`에 현재·보관 상태, 상대경로, 주 파일 SHA-256과 전환 메모를 기록해야 함
- 버전 번호·사용자 지정 기준본·해시가 충돌하거나 산출물군을 확정할 수 없으면 자동 이동하지 않아야 함
- 공고·RFP·원본 양식·근거자료, 서로 다른 접수·서명 증거와 사용자가 병렬로 유지하도록 지정한 대안은 임의로 구버전 처리하지 않아야 함
- 접수번호·서명·제출시각이 특정 해시와 연결된 실제 제출 완료 파일은 자동 이동·이름변경·덮어쓰기하지 않고, 정정은 별도 재제출 후보 산출물군으로 만들어야 함
- 읽기 전용 검토·진단·제출점검에서는 기존 파일을 이동하거나 버전 이력을 수정하지 않아야 함
- 보관 경로 충돌, 파일 잠금 또는 부분 이동이 발생하면 덮어쓰거나 삭제하지 말고 복구 후 정확한 위치와 잔여 조치를 보고해야 함
- 파일 이동 전 상대경로·대상경로·SHA-256과 이력표 백업을 `recovery-manifest.json`에 남기고, 승격·해시검증·이력 갱신 중 하나라도 실패하면 작업 전 상태로 복구해야 함
- HWPX 검증 증거를 이전 버전과 함께 보관할 때 원본 영수증은 수정하지 않고 `evidence-relocation-map.json`으로 화면·프리뷰의 이전 경로와 보관 경로를 연결해야 함
- 보관본을 다시 사용할 때는 보관 파일을 제자리에서 수정하지 않고 이를 기준으로 번호가 올라간 새 버전을 만들어야 함

## 최신 산출물 내용 연동

- 새 후보와 그 산출물군의 이전 현재본을 의미 단위로 비교한 뒤, `산출물_버전이력.md`의 다른 현재 산출물 중 실제 영향을 받는 파일만 새 버전으로 갱신해야 함
- KPI·예산·기관 역할·기간·과업·실증 변경은 승인된 항목별 원천에서 계획서·발표자료·요약본으로 단방향 전파하고, 발표자료·PDF·검토보고서의 고유 값은 자동 역전파하지 않아야 함
- 단순 맞춤법·조판·서식 변경은 다른 산출물의 내용 버전을 만들지 않아야 함. HWPX의 같은 버전 PDF·프리뷰·검증기록 재생성은 독립 산출물 연동과 구분해야 함
- 서로 다른 산출물군의 버전 번호는 독립적으로 유지하고, 같은 변경 집합으로 갱신된 산출물을 하나의 연동 ID로 연결해야 함
- 정규화된 변경 집합의 SHA-256 지문을 기록하고, 같은 지문과 소비 산출물 해시가 이미 완료 상태면 새 버전·중복 이력을 만들지 않아야 함
- 모든 필수 후보를 먼저 만들고 형식별 검증한 뒤 함께 승격해야 함. 하나가 실패하거나 승격 직전 현재본 해시가 바뀌면 기존 현재본과 두 이력을 유지하고 부분 완료라고 보고하지 않아야 함
- 외부에서 이미 현재본 하나가 바뀐 경우 미갱신 소비 산출물을 `연동 대기`로 기록하고, 제출에 필요한 연동이 남으면 Gate와 `보완 필요`로 판정해야 함
- 읽기 전용 검토·제출점검은 불일치를 보고할 수 있지만 파일·버전 이력·연동현황을 수정하지 않아야 함
- 공고·RFP·양식·근거, `98_이전버전`, 과거 검토보고서, 서명·접수·실제 제출본은 자동 연동으로 수정하지 않아야 함
- 이미 같은 변경 집합을 반영한 연동을 다시 실행해도 새 버전이나 중복 이력 행을 만들지 않아야 함

## bizplan-draft 대화형 설계

### 신규 전체 초안

- RFP와 빈 양식에 `초안 작성해줘`라고 요청해도 첫 응답에서 DOCX·HWPX나 전체 초안을 만들지 않아야 함
- 자료에서 파악한 내용, 실행대안·추천안과 영향도 높은 질문을 제시하고 답변을 기다려야 함
- 답변이 부분적이면 `현재까지 합의`, `실현가능성 조정`, `남은 결정`을 갱신하고 다음 핵심 질문을 이어가야 함
- 핵심 여덟 영역에 `결정 필요`가 남은 동안 전체 문서 작성으로 넘어가지 않아야 함
- 구현 브리프를 사용자에게 보여주고 진행 의사를 확인받은 뒤 양식 배분표와 문서를 작성해야 함

### 양식 배분과 밀도

- 모든 실질 작성영역을 평가질문, 핵심 주장, 근거, 수행·검증, 표현 단위와 내용 예산에 연결해야 함
- 렌더 후 큰 빈 공간을 내용 공백, 배분 불균형, 레이아웃 문제와 양식 고정영역으로 구분해야 함
- 내용 부족을 반복문장, 근거 없는 수치·형용사 또는 장식용 도표로 채우지 않아야 함

### 명시적 즉시 작성

- 사용자가 `질문 없이 가정해서 바로 작성`처럼 대화 생략을 명시한 경우에는 보수적인 실행안을 선택하고 가정·결정 필요를 공개한 뒤 진행할 수 있음
- 일반적인 `초안 작성`, `양식에 넣기` 요청은 즉시 작성 지시로 취급하지 않아야 함
