# 최신 산출물 간 내용 연동

관리 산출물의 내용이 바뀌면 같은 프로젝트에서 함께 사용하는 최신 산출물을 의미 단위로 비교하고, 실제로 영향을 받는 산출물만 새 버전으로 갱신함. 한 파일의 문구를 다른 파일에 무조건 복사하는 양방향 동기화는 하지 않음

## 1. 적용 시점과 최신 산출물 영역

- 에이전트가 DOCX·HWPX·PPTX·XLSX·PDF·반영대장 등 관리 산출물을 새로 만들거나 수정해 기존 현재본과 의미가 달라질 때 적용함
- 공식 RFP·공식 Q&A의 새 revision 또는 승인된 KPI·예산·일정·역할 원장의 갱신이 확인되고 사용자가 현재 산출물 갱신을 요청한 경우에도 적용함. 공식 원천 자체는 수정하지 않고 그 변경 집합을 소비하는 현재 산출물만 갱신함
- 사용자가 `최신 산출물` 폴더를 지정했거나 그 이름의 관리 폴더가 이미 있으면 그 영역을 우선 확인함. 표준 AX1 작업공간에서는 `08_작성중`, `09_검토_수정`, `10_제출본`을 통틀어 현재로 관리되는 산출물 묶음이 최신 산출물 영역임
- 최신본을 한곳에 복제하기 위한 별도 폴더는 만들지 않음. 같은 파일의 복사본을 여러 곳에 두면 어느 쪽이 기준인지 다시 모호해짐
- 서식·띄어쓰기·페이지 나눔만 바뀌고 사업 내용이 같으면 독립 산출물의 내용 연동은 하지 않음. 같은 버전의 PDF·프리뷰·검증기록처럼 종속 파일만 다시 생성·검증함
- 대화 결과나 읽기 전용 검토·진단·제출점검은 다른 파일을 수정할 권한이 아님. 사용자가 파일 수정까지 요청했거나 현재 작업 자체가 산출물 생성·수정 작업일 때만 실제 연동본을 만듦

## 2. 항목별 기준 원천

파일 전체가 아니라 변경 항목마다 기준 원천을 정함

| 역할 | 의미 | 기본 처리 |
|---|---|---|
| 공식 원천 | 공고·RFP·공식 양식·공식 Q&A | 읽기 전용 최상위 근거이며 산출물에 맞춰 고치지 않음 |
| 승인 원천 | 사용자가 확정한 결정, 기관 합의, 승인된 KPI·예산·일정 원장 | 해당 항목의 기준값으로 사용함 |
| 주 산출물 | 사업계획서처럼 서술과 수행구조를 가장 완전하게 담은 현재본 | 발표자료·요약본 등 파생 산출물의 내용 기준이 될 수 있음 |
| 파생 산출물 | 발표자료, 요약본, PDF, 제출용 형식본처럼 다른 원천을 축약·변환한 파일 | 기준 원천의 확정 변경만 목적과 분량에 맞게 반영함 |
| 진단 산출물 | 검토보고서, 점검표, 제안 상태의 반영대장 | 승인된 사실의 기준으로 자동 승격하지 않음 |
| 이력·증거·제어 파일 | `98_이전버전`, 서명·접수·승인 증거, 버전·연동 이력 | 사업 내용의 전파 대상으로 편집하지 않음. 두 이력은 트랜잭션 결과만 갱신함 |

- 예산 원장, KPI 원장, 기관 역할 합의서처럼 항목별 전용 승인 원천이 있으면 사업계획서보다 우선함
- HWPX나 발표자료에서만 발견된 고유 수정은 자동으로 전체 프로젝트의 새 기준으로 삼지 않음. 기존 기준의 누락인지, 승인된 신규 결정인지 확인해 별도 변경 집합으로 분리함
- 공고·승인 원천과 후보 산출물이 충돌하거나 예산·기관·기간·법적 의무·승인 KPI처럼 권한이 필요한 값을 바꾸려면 `승인 필요`로 두고 임의 전파하지 않음

## 3. 의미 변경 집합

기존 현재본과 새 후보를 비교해 `변경 집합`을 먼저 만듦. 단순 파일 해시나 수정일만으로 영향 여부를 결정하지 않음

변경 집합에는 다음을 기록함

- 연동 ID: `SYNC-YYYYMMDD-HHMMSS-짧은식별자`
- 변경 집합 지문: 원천 산출물군·이전/후 버전, 정렬된 변경 영역·항목·이전/후 값·근거 상태의 canonical JSON을 SHA-256으로 계산한 `changeSetHash`
- 원천 산출물군, 이전·후 버전과 프로젝트 상대경로
- 변경 영역과 항목, 이전 값, 새 값
- 근거 원천과 `확정 / 가정 / 승인 필요` 상태
- 영향을 받을 수 있는 최신 산출물군과 반영 위치

우선 비교할 영역은 과제명, 기관명·역할, 기간, 예산, 최종·연차 목표, KPI·측정법, 과업·마일스톤, 기술·데이터 범위, 실증, 산출물, 사업화와 주요 위험임. 문장 표현이 달라도 같은 의미면 불필요한 버전을 만들지 않음

## 4. 영향도 판정

1. 최신 산출물 영역과 `산출물_버전이력.md`를 확인해 산출물군별 현재본을 목록화함
2. `산출물_연동현황.md`가 있으면 기준 원천과 소비 관계를 사용하고, 없거나 비어 있으면 실제 파일의 제목·표·수치·참조 관계를 읽어 이번 작업에 필요한 관계를 판정함. 쓰기가 허용된 산출물 갱신 작업에서만 관계를 파일에 등록하며 읽기 전용 작업은 메모리상 분석만 수행함
3. 각 변경 항목이 현재 산출물에 직접 기재되었는지, 계산·요약·도표·일정·역할의 입력으로 쓰였는지 확인함
4. `반영 필요 / 영향 없음 / 승인 필요 / 편집 불가 / 확인 불가 / 이력·증거 제외`로 판정함
5. 반영이 필요한 위치와 전후 값을 확정한 뒤에만 파일 편집을 시작함

`필수 영향 산출물`은 원천 후보와 같은 현재 작업·검토·제출 묶음에서 실제로 함께 사용할 산출물 중 변경 항목을 직접 표시하거나 그 항목으로 계산·요약·도표화하는 파일임. 영향을 받는 활성 현재본은 기본적으로 필수이며, 현재 제출 후보 본문·발표자료·필수 요약·승인 원장은 이에 포함됨. 과거 보고서·증거·중단된 대안과 사용하지 않는 내부 참고본은 제외 사유를 기록한 경우에만 비필수로 분류함. 활성 여부가 모호하면 임의로 비필수 처리하지 않고 확인함

다음은 일반적인 영향 예시임

- KPI 목표 변경 → 계획서의 목표·연차·측정표, KPI 원장, 발표자료의 성과 슬라이드
- 기관 역할 변경 → 추진체계, 기관별 과업·일정·예산 설명, 발표자료의 역할 도식
- 사업기간 변경 → 개요, 연차계획, 간트·마일스톤, 예산 연도와 제출 요약
- 서술 표현만 정리 → 그 문장을 실제로 소비하는 요약·발표자료만 영향 검토하고 독립 근거·증거는 유지

## 5. 한 번의 연동 트랜잭션

에이전트가 만드는 변경은 다음 순서로 하나의 연동 트랜잭션으로 처리함

1. 주 변경 후보와 영향을 받는 모든 현재 산출물의 후보 버전을 `99_임시작업/산출물연동/<연동ID>/` 아래에 서로 다른 파일명으로 만듦
2. 각 산출물의 형식에 맞는 전용 문서·프레젠테이션·스프레드시트·HWPX 절차로 수정함. PDF처럼 안전하게 직접 편집할 수 없는 파생본은 편집 가능한 기준본에서 다시 생성함
3. 후보별 내용 readback, 수치·용어 정합성, 구조와 시각 상태를 검증하고 이전 값이 정당한 역사 문맥이 아닌 현재 문맥에 남았는지 검색함
4. `sync-manifest.json`에 `schemaVersion: "ax1.artifact-sync/v1"`, 연동 ID, `changeSetHash`, 원천 변경 집합, 원천·대상 산출물군별 독립 버전·현재 경로·작업 전 SHA-256·후보 경로·후보 SHA-256·필수 여부·판정·검증 상태를 기록함. `산출물_버전이력.md`와 `산출물_연동현황.md`의 작업 전 존재 여부를 `versionLedgerExistedBefore`, `syncLedgerExistedBefore`로 기록하고, 존재했다면 작업 전 사본 경로·SHA-256도 `versionLedgerBackupPath`, `syncLedgerBackupPath`로 남김. `phase`와 순서가 있는 `operations` 배열에는 각 이동·승격·이력 갱신의 예정 작업, 실행 상태와 정확한 역연산을 기록하고 파일을 바꾸기 전에 journal을 먼저 저장함
5. 승격 직전에 모든 현재본의 revision 또는 SHA-256을 다시 읽어 작업 시작 후 다른 변경이 없었는지 확인함
6. 필수 영향 산출물 하나라도 안전하게 만들거나 검증하지 못하면 에이전트가 생성한 주 변경 후보도 현재본으로 승격하지 않음. 기존 현재본은 그대로 두고 `연동 대기` 또는 `차단`으로 보고함
7. 모두 통과하면 산출물 최신본·이전버전 관리 규칙의 복구 명세를 전체 산출물군에 대해 먼저 만든 뒤, 기존 묶음 보관·새 묶음 승격·버전 이력·연동 이력을 한 작업으로 갱신함
8. 이동·승격·이력 갱신 중 하나라도 실패하면 전체 트랜잭션을 작업 전 상태로 복구함. 원래 있던 이력은 작업 전 사본으로 되돌린 뒤 SHA-256을 확인하고, 원래 없어서 이번 트랜잭션이 만든 이력은 manifest의 생성 후 SHA-256과 정확히 일치할 때만 해당 프로젝트의 정확한 이력 경로에서 제거하는 역연산을 수행함. 예상하지 못한 동시 변경 때문에 복원·제거가 안전하지 않으면 덮어쓰거나 삭제하지 않고 중단하며 부분 완료라고 보고하지 않음

사용자나 외부 편집기가 이미 최신 영역의 한 파일을 변경해 이전 상태로 되돌릴 수 없는 경우에는 그 파일을 원천 후보로 보존한 채 나머지를 최대한 연동함. 완료하지 못한 소비 산출물은 `연동 대기`로 기록하고, 모든 필수 산출물이 맞춰질 때까지 `10_제출본`을 `준비`로 판정하지 않음

## 6. 반복 전파와 충돌 방지

- 한 연동 ID 안에서 각 산출물군은 최대 한 번만 갱신함
- 같은 `changeSetHash`가 해당 소비 산출물의 현재 버전에 `연동 완료`로 기록되어 있고 현재 SHA-256도 일치하면 다시 편집하거나 중복 이력 행을 만들지 않고 `영향 없음(이미 반영)`으로 처리함. 지문은 같지만 소비 산출물의 버전·해시가 달라졌으면 새 상태에서 영향도를 다시 판정함
- 파생 산출물의 갱신은 같은 변경 집합을 소비한 결과이며 새 원천 변경으로 다시 순환시키지 않음
- 파생본 편집 중 변경 집합에 없던 고유 정보가 나타나면 별도 제안으로 멈추고 기준 원천과 승인 상태를 판정함
- 여러 원천에서 같은 항목을 다르게 제시하면 수정시각으로 승자를 정하지 않고 공식성·승인 상태·사용자 지정 기준을 비교함
- 동시에 다른 작업자가 파일을 수정했거나 읽은 뒤 revision·해시가 바뀌면 현재 트랜잭션을 중단하고 새 상태에서 영향도를 다시 계산함
- 서로 다른 산출물군의 버전 번호를 억지로 같게 만들지 않음. 계획서 `v04`와 발표자료 `v07`도 같은 연동 ID로 정합 상태가 될 수 있음

## 7. 제출·증거 예외

- `10_제출본`의 미제출 승인 후보는 새 버전을 만들고 재검증·재승인할 수 있음
- 이미 서명·접수·제출된 파일은 불변 사건 기록이므로 자동 수정하지 않음. 변경이 필요하면 기존 파일을 고치지 않고 `정정·재제출 후보`라는 새 산출물군으로 만들어 사람의 승인을 받음
- 접수증·서명본·승인기록과 과거 검토보고서는 현재 내용과 달라도 당시 상태의 증거이므로 수정하지 않음

## 8. 연동 상태와 기록

프로젝트 최상위의 `산출물_연동현황.md`에 영역·항목별 기준 원천, 소비 산출물의 마지막 반영 지문과 트랜잭션 결과를 기록함. 기존 작업공간에 이 파일이 없으면 쓰기가 허용된 산출물 갱신 작업에서만 배포 스킬의 `assets/artifact-sync-ledger-template.md`를 복사해 만들되 기존 산출물은 이동하지 않음. 읽기 전용 작업은 파일을 만들거나 갱신하지 않음

허용 상태는 다음과 같음

- `연동 완료`: 필요한 모든 최신 산출물의 새 버전과 검증이 완료됨
- `영향 없음`: 비교했으나 해당 산출물에 반영할 의미 변경이 없음
- `연동 대기`: 필요한 변경은 식별했지만 입력·도구·검증이 남음
- `차단`: 충돌·잠금·부분 실패로 안전한 전환을 하지 못함
- `승인 필요`: 권한 있는 사람의 결정 전에는 전파할 수 없음
- `이력·증거 제외`: 불변 자료이므로 비교만 하고 편집하지 않음

이력에는 민감한 본문 전체를 복사하지 말고 변경 영역과 필요한 최소 요약만 기록함. 표 안의 줄바꿈은 `<br>`, 세로줄은 이스케이프해 표 구조를 보존함
