# 목적

제공된 양식의 논리구조를 보존하고, 공식 자료와 사용자의 사업 구상을 결합해 실현 가능한 수행체계로 다듬은 뒤 안정적으로 편집·검증할 수 있는 사업계획서 초안을 작성함

# 진행 기본값

- 현재 대화와 작업 폴더에서 접근 가능한 자료를 먼저 찾아 사용하고, 이미 제공된 파일을 다시 요청하지 않음
- 일부 자료가 없어도 자료 분석과 대화형 구체화는 가능한 범위부터 진행하되, 핵심 결정이 비어 있으면 전체 초안 작성으로 넘어가지 않음. 방향을 바꾸지 않는 미확정 값만 `〈자료 필요: 값·담당〉`으로 표시함
- 전체 초안, 빈 양식 작성, 여러 장의 대규모 보완은 `대화형 사업 설계`를 기본 모드로 사용함. 사용자의 `초안 작성해줘`라는 표현만으로 질문 생략을 추론하지 않음
- 질문은 한 번에 모두 쏟지 않고 답변에 따라 사업 설계 보드를 갱신하며 필요한 다음 질문을 이어감. 각 질문 회차 뒤에는 답변을 기다리고, 그 사이 전체 문서 파일을 만들지 않음
- 사용자의 답변이 거칠거나 부분적이어도 대상·사용 시나리오·구현경계·가용자원·과업·검증·사업화 구조로 정제하고, 합의된 결정과 남은 공백을 구분함
- 사용자가 `질문 없이`, `가정해서 바로`, `인터뷰 생략`을 명시한 경우에만 즉시 작성 모드로 전환함. 이때도 실행대안과 가정을 먼저 제시하고 가장 보수적으로 실현 가능한 안을 선택하되 가정을 승인 사실처럼 쓰지 않음
- 단순 수치·기관명처럼 나중에 채울 정보는 결과물 끝의 확인 항목으로 묶음. 대화형 사업 설계 모드에서는 사업 방향이나 구현 구조를 바꾸는 핵심 정보를 구체화 게이트 전에 질문하고, 즉시 작성 모드에서는 보수적 추천 가정과 결정 필요로 분리해 공개함
- 사용자가 파일 형식을 지정하지 않은 문서 산출물은 DOCX를 기본으로 함. HWPX는 원본 구조 보존과 재개방·시각 검증이 가능한 경우에만 사용하고, 바이너리 HWP는 편집 결과 형식으로 만들지 않음
- 사용자가 HWPX 양식 작성본을 요청하면 먼저 내용 초안을 확정한 뒤 `bizplan-hwpx`로 양식 매핑·원본 보존·모의 편집·한컴 재개방 검증을 수행함
- 사용자가 실제 문서 파일의 생성·수정을 요청한 경우에만 [작업 파일 처리](references/07-artifact-workflow.md)를 읽고 적용함
- 기존 현재본과 의미가 달라지는 문서 파일을 만들면 [최신 산출물 간 내용 연동](references/11-artifact-synchronization.md)을 읽고 KPI·예산·기관 역할·일정·과업·실증 등 변경 집합이 다른 최신 산출물에 미치는 영향을 확인함. 필요한 산출물은 각각 새 버전으로 함께 만들고 검증하며, 단순 서식 변경은 전파하지 않음

# 시작 조건

먼저 다음 자료를 현재 대화와 작업 폴더에서 탐색하고 확보 상태를 기록함

1. 공고문·RFP·공식 Q&A
2. 작성 양식과 양식 내 작성지침
3. 평가배점표
4. 최신 프로젝트 자료와 승인된 수치·역할
5. 작성할 항목과 검토 제외범위
6. 사용자가 구상한 사업 진행 아이디어, 구현 방식과 실제 가용자원
7. 제출 요구 형식과 기준 양식의 파일 형식
8. 양식 항목별 작성지침, 평가배점, 페이지·글자 수 제한과 고정된 빈 영역

RFP가 없더라도 사용자가 일반 초안을 요청하면 진행할 수 있으나, 목표값과 필수요건을 확정하지 않고 자료 한계를 명시함

# 작업 절차

## 1. 소스 인벤토리와 기준문서 확정

[범용 코어 원칙](references/01-core-principles.md)과 [소스 인벤토리 템플릿](assets/source-inventory-template.md)을 사용함

- 충돌하는 문서가 있으면 최신 기준문서를 먼저 지정함
- 공고·양식·작성지침을 다른 사례보다 우선함
- 평가의견의 반영문안을 공식 정답으로 취급하지 않음

## 2. 대화형 사업 설계와 구체화 게이트

[사업 구체화·실현가능성 설계](references/08-concept-feasibility.md)를 읽고 적용함

- 전체 초안이면 자료가 어느 정도 있어도 먼저 사업 설계 상태를 확인함. 좁은 단일 항목 보완만 요청했고 상위 사업 설계가 이미 확정된 경우에는 필요한 공백만 짧게 확인함
- 첫 회차에는 RFP와 제공자료에서 파악한 사실, 잠정 사업상과 핵심 공백을 요약하고 사용자가 이미 준 답을 다시 묻지 않음
- 대상 고객·현장과 해결문제, 사용 시나리오, 구현 흐름, 가용 데이터·설비·인력, 참여기관 역할, 실증·사업화 경로 중 초안의 내용이 달라질 핵심 공백을 판정함
- 핵심 선택에는 RFP에서 도출한 2~3개 실행대안과 추천안을 먼저 보여주고, 사용자가 짧게 선택·수정할 수 있는 질문을 보통 3~5개, 최대 7개까지 제시한 뒤 답변을 기다림
- 다음 회차에는 답변을 반영한 `현재까지 합의`, `실현가능성 조정`, `남은 결정`을 먼저 갱신하고, 새로 드러난 핵심 공백만 이어서 질문함
- 질문은 양식의 단순 빈칸을 채우기 위한 것이 아니라 `무엇을, 누가, 어떤 자원으로, 어떻게 만들고, 어디서 검증·운영·구매할지`를 확정하는 데 집중함
- 사용자가 잘 모르겠다고 답하면 합리적인 대안, 장단점과 추천 기본값을 제시함
- 대상·문제, 사용·가치, 구현 흐름, 구현경계·역할, 가용자원, 과업·연차, KPI·실증, 도입·사업화의 핵심 선택이 `확인`, `사용자 선택` 또는 사용자가 수용한 `추천 가정`으로 정리되고 서로 모순되지 않으며 핵심 `결정 필요`가 없을 때만 구체화 게이트를 통과함
- 사용자가 즉시 작성을 명시하면 추천안을 임시 채택하여 계속 진행하고 `가정`과 `결정 필요`를 분리함

핵심 구현구조가 불명확한 상태에서는 전체 문서 파일이나 양식 채움 작업을 시작하지 않음. 기존 자료에 구현 브리프 수준의 내용이 있더라도 먼저 요약해 보여주고 사용자가 계속 진행하거나 수정할 기회를 제공함

## 3. 구현 브리프와 실현가능성 정제

답변과 근거를 결합해 다음을 1~2페이지 분량의 구현 브리프로 먼저 정리함

- 한 문장 가치제안과 구체적 대상·문제
- 도입 전·후 업무 또는 운영 시나리오
- 핵심 기능·기술 구성요소와 데이터·물류·의사결정 흐름
- 자체 개발, 외부 연계, 총괄·타 세부 제공기술의 경계
- 과업별 입력·활동·산출물·검증·책임기관·선후행관계
- 연차별 마일스톤과 다음 단계 진입조건
- 기준선·목표·측정방법이 연결된 핵심 KPI
- 현장 실증, 안전·규제·보안, 실패 시 대안
- 초기 수요처, 도입·운영주체, 수익·확산 경로
- 확인·가정·결정 필요 항목

예산·기간·인력·데이터·설비·기술성숙도·외부의존성과 비교해 범위를 점검하고, 과도한 구상은 핵심 PoC → 제한 실증 → 확산 단계로 축소·분할함. 사용자의 원안을 조용히 바꾸지 말고 조정 이유와 보존한 핵심가치를 함께 제시함

전체 초안에서는 구현 브리프의 핵심 선택, 범위조정과 가정을 사용자에게 보여주고 `이 방향으로 양식 배분과 초안을 진행`해도 되는지 확인함. 사용자가 계속 진행 의사를 표현하거나 즉시 작성 모드를 명시하기 전에는 양식 파일을 채우지 않음

## 4. 양식과 스타일 프로파일 작성

[양식·문체·편집 가이드](references/02-format-style-guide.md)와 [문서 스타일 프로파일](assets/document-style-profile-template.md)을 사용함

- 대·중·소제목의 단계와 명칭, 들여쓰기, 표 구조를 유지함
- 한국어 정부 R&D 기본 문체는 `~함`, `~임`과 같은 명사형 종결 및 마침표 미사용으로 두되 양식이 다르면 양식을 우선함
- 그림-그림, 표-표가 설명 없이 연속되지 않도록 구성함
- 도표 앞에는 목적, 뒤에는 핵심 해석을 둠

## 5. 양식 배분과 내용 밀도 설계

[양식 매핑·내용 밀도 설계](references/09-form-allocation-density.md)를 읽고 적용함

- 양식의 모든 실질 작성 항목에 평가질문, 구현 브리프의 근거, 핵심 주장, 수행·검증 내용과 표현 단위를 연결한 `양식 배분표`를 먼저 만듦
- 배점·페이지 제한·작성지침에 따라 항목별 내용 예산을 정하고, 핵심 내용이 한 장에 몰리거나 관련 항목이 형식적인 한두 문장으로 끝나지 않게 분산함
- 큰 빈 공간이 예상되면 내용 공백, 레이아웃 문제, 양식이 의도한 고정 여백을 구분함. 내용 공백이면 질문 또는 구현 브리프로 돌아가고, 문장을 반복하거나 도표를 장식용으로 추가하지 않음
- 같은 설명을 여러 항목에 복제하지 않고 각 항목의 평가질문에 맞게 필요성·방법·검증·활용의 역할을 나눔

## 6. 작성 항목의 논리 골격 설정

작성 전에 다음 순서를 1줄씩 정리함

- 이 항목이 답해야 할 평가질문
- 핵심 주장
- 공식·프로젝트 근거
- 수행방법
- 검증방법
- 산출물과 다음 항목과의 연결

## 7. KPI가 있으면 유형별 원장 작성

[KPI 프레임워크](references/04-kpi-framework.md)와 [지표 원장 템플릿](assets/indicator-ledger-template.csv)을 사용함

- 성능형·데이터형·실증형·성과형·사업화형을 구분함
- 모든 지표에 같은 시험필드를 강제하지 않음
- 성능형 지표는 기준선·산식·대상·시료·반복·기간·검증을 확인함
- 수치를 모르면 `〈자료 필요: 값·담당〉`으로 남김

## 8. 초안 작성

- 양식의 제목과 표 구조 안에서 작성함
- 공고 용어를 임의로 바꾸지 않음
- 하나의 문단은 하나의 핵심 주장에 집중함
- 장식적 표현보다 대상·범위·방법·책임·검증을 우선함
- 주요 과업은 가능한 범위에서 `입력 → 수행활동 → 산출물 → 검증 → 책임 → 연차·의존성`이 드러나게 씀
- 구현 방식은 기술명 나열이 아니라 사용 주체, 작동 순서, 데이터·설비 인터페이스와 예외·안전 처리까지 운영 시나리오로 설명함
- 실증과 사업화는 연구개발 결과를 누가 어떤 조건에서 도입·검증·구매·운영하는지 연결함
- 양식 배분표의 내용 예산을 기준으로 항목별 핵심 주장·방법·산출물·검증이 빠짐없이 들어갔는지 확인하면서 작성함
- 사업 프로파일의 적용조건이 맞을 때만 [PI-LAM 프로젝트 프로파일](references/05-project-profile.md)을 추가 적용함

## 9. 자체 점검

- 새 항목을 만들어 양식을 변경하지 않았는가
- 제목 단계와 들여쓰기가 주변 항목과 같은가
- 명사형 종결과 마침표 규칙이 통일되었는가
- 표·그림 번호와 본문 참조가 일치하는가
- 같은 수치와 용어가 다른 장과 충돌하지 않는가
- 사실처럼 보이는 추정치가 없는가
- 그림·표가 설명 없이 연속되는가
- RFP의 표현을 다시 배열한 수준에 머물지 않고 사용자의 사업 구상과 구현 선택이 반영되었는가
- 핵심 과업마다 구체적인 수행주체·입력·방법·산출물·검증이 있는가
- 연차계획이 활동 목록이 아니라 산출물과 다음 단계 진입조건으로 연결되는가
- 실증·운영·사업화 경로가 실제 가용자원과 모순되지 않는가
- 양식의 모든 실질 작성 항목이 구현 브리프와 연결되고, 핵심 항목이 일반적인 한두 문장이나 `확인 필요`만으로 끝나지 않는가
- 렌더된 페이지의 큰 빈 공간이 내용 부족, 불필요한 페이지 나눔·표 높이, 양식 고정영역 중 무엇 때문인지 구분했는가
- 내용 부족으로 생긴 빈 공간을 발견했을 때 반복문장·과장·장식용 도표로 채우지 않고 구체화 질문이나 양식 배분으로 되돌아갔는가
- 한글 글리프 누락·깨짐, 글꼴 대체, 표 잘림과 문단 재배치가 없는가

# 출력

텍스트 작성을 요청한 경우

구체화 게이트 전에는 회차마다 다음을 제공하고 답변을 기다림

1. `현재까지 파악·합의한 내용`
2. `실현가능성 조정 또는 실행대안·추천안`
3. `남은 핵심 결정`
4. `이번 회차 질문`

구체화 게이트를 통과하면 `구현 브리프`, 범위조정, 가정과 결정 필요 항목을 먼저 보여주고 전체 초안 진행 여부를 확인함. 사용자가 진행을 확인한 뒤에는 다음을 제공함. 단, 즉시 작성 모드에서는 사용자의 명시를 진행 확인으로 간주함

1. `구현 브리프` - 선택한 실행안, 범위조정과 핵심 가정
2. `양식 배분표` - 항목별 평가질문, 배치할 내용, 표현 단위, 내용 예산과 공백
3. `작성 방향` - 평가질문과 논리구조
4. `직접 삽입 가능한 초안`
5. `표·그림 제안` - 필요한 경우에만, 위치와 목적 포함
6. `확인 필요 항목` - 값, 담당, 미확보 영향
7. `출처·가정 메모`

실제 문서 파일 작성을 요청한 경우 별도 형식 지정이 없으면 DOCX 수정본을 제공함. 전체 초안은 대화형 구체화와 구현 브리프 확인을 거친 뒤 작성함. DOCX는 Word 문서 전용 작성 절차로 생성하고 모든 페이지를 렌더하여 양식 배분표와 대조하며 큰 빈 공간·표 잘림·고립 제목을 확인한 뒤 수정 위치, 검증 결과와 남은 확인 항목을 함께 제공함. HWPX가 필요한 경우에는 내용 초안을 확정한 뒤 `bizplan-hwpx`로 넘기고 [작업 파일 처리](references/07-artifact-workflow.md)의 구조·readback·프리뷰·한컴 검증 기준을 충족할 때만 제출 후보로 제공함. 새 버전의 의미 변경이 다른 최신 산출물에 영향을 주면 필수 연동 후보까지 함께 검증한 뒤 각 산출물군의 기존 현재본 묶음을 삭제하지 않고 `98_이전버전`으로 보관하며 버전 이력과 `산출물_연동현황.md`를 갱신함

# 금지

- 사용자가 제공한 양식의 제목·번호·표를 임의 변경하지 않음
- 다른 사업의 수치·기관·문구를 사실처럼 복사하지 않음
- 자료가 없다는 이유로 시장규모·목표값·시험조건을 생성하지 않음
- 구현 구상이 비어 있는데 RFP 문구를 확장해 완성된 사업 아이디어처럼 쓰지 않음
- 핵심 사업결정을 단순 `확인 필요`로 뒤로 미룬 채 전체 초안을 먼저 작성하지 않음
- 사용자의 일반적인 `초안 작성` 요청을 `질문 없이 바로 작성`으로 해석하지 않음
- 대화형 구체화 회차에서 답변을 기다리지 않고 질문과 전체 초안을 같은 응답에 함께 제공하지 않음
- 구현 브리프의 방향 확인 전에 전체 양식 파일을 채우지 않음
- 사용자의 아이디어를 타당성 검토 없이 그대로 과업·목표로 확정하지 않음
- DOCX 파일의 확장자만 바꾸어 HWP·HWPX로 전달하지 않음
- 바이너리 HWP 원본을 직접 덮어쓰거나 HWP 편집본을 생성하지 않음
- HWPX의 구조·재개방·시각 상태를 확인하지 않고 제출 가능한 최종본이라고 보고하지 않음
- 형식 변환 후 원본 양식과 시각적으로 동일하다고 검증 없이 단정하지 않음
- 모든 문단을 길게 늘려 `구체화`로 오해하지 않음
- 도표를 페이지 채우기 용도로 추가하지 않음
