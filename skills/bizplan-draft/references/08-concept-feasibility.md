# 사업 구체화·실현가능성 설계

## 목적

공고문과 RFP가 제시하는 `해야 할 일`을 사용자의 실제 사업 구상과 연결하여 `어떻게 수행하고 검증·운영할지`까지 확정함. 이 단계의 결과는 일반적인 목차나 아이디어 목록이 아니라 초안의 과업·연차·KPI·실증·사업화 내용을 결정하는 구현 브리프임

## 1. 먼저 자료에서 답을 찾음

질문 전에 RFP, 양식, 프로젝트 자료에서 다음을 추출함

- 필수 대상, 성과, 기술·정책 제약과 제외범위
- 사업기간, 예산, 목표 TRL·실증단계와 정량 요구
- 총괄·세부·수요기관 등 지정된 역할과 연계조건
- 사용자가 이미 언급한 아이디어, 보유기술, 현장, 데이터, 인력과 수요처

확인된 내용을 3~7개 항목으로 짧게 되짚고, 근거가 있는 내용은 다시 질문하지 않음

## 2. 핵심 공백 판정

다음 중 하나가 빠져 선택에 따라 초안의 구조가 달라지면 구체화 질문이 필요함

| 영역 | 확인할 내용 | 초안에 미치는 영향 |
|---|---|---|
| 대상·문제 | 누가, 어디서, 어떤 손실·불편·위험을 겪는가 | 필요성, 목표, 시장 |
| 가치·사용 | 최종 사용자가 결과물을 언제 어떻게 쓰는가 | 기능, 운영 시나리오 |
| 구현 흐름 | 입력 데이터·자원에서 결과·조치까지 어떤 단계로 작동하는가 | 연구내용, 시스템 구성 |
| 가용자원 | 실제 확보 가능한 데이터, 설비, 현장, 인력, 선행기술은 무엇인가 | 범위, 일정, 실현가능성 |
| 역할·연계 | 누가 개발·제공·통합·검증·운영하는가 | 추진체계, 책임, 의존성 |
| 실증·검증 | 어디서 무엇과 비교해 성공을 판정하는가 | KPI, 시험계획, 산출물 |
| 사업화·확산 | 최초 고객과 도입·구매·운영 방식은 무엇인가 | BM, 수익, 확산계획 |
| 제약·리스크 | 기간·예산·규제·안전·보안·조달 제약은 무엇인가 | 단계화, 대안, 관리계획 |

기관명·담당자·정확한 예산 같은 단순 빈칸은 초안 후 확인할 수 있음. 반대로 대상현장, 핵심 사용자, 구현경계, 실증 가능성처럼 사업 설계를 바꾸는 공백은 먼저 확인함

## 3. 질문 방식

빈 종이에서 답하게 하지 말고 다음 순서로 진행함

1. 자료에서 도출한 잠정 사업상을 2~4문장으로 설명함
2. 구현 방식이 여러 개면 실행대안 2~3개를 제시함
3. 각 대안의 차이를 범위, 필요자원, 장점, 리스크로 비교함
4. RFP 적합성과 현재 가용정보를 기준으로 추천안을 하나 표시함
5. 사용자가 선택·수정하거나 짧게 답할 수 있는 질문을 한 번에 최대 7개까지 묻고 답변을 기다림

질문 예시는 아래와 같으며, 모두 묻지 않고 실제 공백만 선택함

1. 이 사업에서 가장 먼저 해결하려는 현장 문제와 최종 사용자는 누구인가
2. 결과물이 현장에서 사용되는 과정을 시작부터 조치·피드백까지 설명하면 어떻게 되는가
3. 직접 개발할 핵심과 기존 제품·타 과제·외부 서비스에서 연계할 부분은 무엇인가
4. 현재 실제로 확보 가능한 데이터·설비·실증현장·전문인력은 무엇이며 언제부터 쓸 수 있는가
5. 참여기관별로 개발, 제공, 통합, 검증, 운영 중 어디까지 맡길 것인가
6. 실증 성공을 무엇과 비교해 어떤 증빙으로 판단할 것인가
7. 첫 도입처가 누구이며 구축비·라이선스·운영서비스 등 어떤 방식으로 확산할 것인가

사용자가 전문용어 없이 경험과 아이디어만 설명해도 됨을 알려 부담을 낮춤. 답을 모른다고 하면 가능한 선택지와 추천 기본값을 제시함. 한 차례 답변 뒤에도 서로 모순되어 문서 방향을 정할 수 없는 핵심 한두 항목만 짧게 재확인함

## 4. 즉시 작성 모드

사용자가 `질문 없이`, `가정해서`, `일단 바로 작성`을 명시하면 질문 때문에 멈추지 않음

- RFP에 부합하는 실행대안 2~3개를 내부적으로 비교함
- 가장 보수적으로 실현 가능한 안을 선택함
- 선택 이유, 필요한 전제와 범위제한을 `가정`으로 표시함
- 사용자가 제공하지 않은 기관·보유기술·현장·매출·성능수치를 만들지 않음
- 핵심 의사결정은 `결정 필요`로 남기고, 결정에 따라 바뀌는 장과 추천 기본값을 함께 적음

즉시 작성은 일반론 작성의 허가가 아님. 선택한 운영 시나리오와 구현 경계를 끝까지 일관되게 적용함

## 5. 실현가능성 정제

사용자의 원안을 다음 기준으로 점검함

### 범위와 자원

- 기간·예산·투입인력 안에서 핵심 기능과 실증을 완료할 수 있는가
- 필요한 데이터·설비·현장 접근권이 실제로 있는가
- 새로 개발할 부분과 구매·도입·연계할 부분이 구분되는가
- 타 세부과제나 외부기관의 선행 산출물과 지연 영향을 정의했는가

### 기술과 운영

- 입력에서 분석·의사결정·현장 조치·피드백까지 흐름이 끊기지 않는가
- 연구용 프로토타입과 실제 운영시스템의 차이를 메울 단계가 있는가
- 안전, 개인정보·보안, 인허가, 통신·센서 장애와 수동전환을 고려했는가
- 목표성능을 비교할 기준선과 재현 가능한 검증방법이 있는가

### 실증과 사업화

- 실증현장의 사용자, 기간, 표본, 대조조건, 합격기준과 증빙이 있는가
- 실증결과가 구매·기술이전·구축·운영 계약으로 이어지는 의사결정 경로가 있는가
- 최초 시장과 확산 시장을 구분하고 유지관리 주체를 정했는가

과도한 범위는 `핵심 PoC → 제한된 현장실증 → 기능·현장 확장`으로 단계화함. 동시에 개발하기 어려운 기능은 우선순위와 제외조건을 제시함. 사용자 원안을 조정할 때는 `위험 → 조정안 → 보존되는 가치` 순서로 설명함

## 6. 구현 브리프

초안 전에 아래 구조를 채우고 장 전체에서 기준으로 사용함

| 항목 | 작성 내용 |
|---|---|
| 한 문장 사업상 | 대상·문제·해결방식·기대변화 |
| 핵심 사용자·현장 | 사용자, 장소, 사용시점과 현재 업무 |
| 도입 전·후 시나리오 | As-is 단계와 To-be 단계, 사람의 승인·개입 |
| 구현 구성 | 데이터·장비·모델·서비스·화면·인터페이스 |
| 구현 경계 | 자체 개발, 도입, 총괄·타 세부 연계, 제외범위 |
| 과업 패키지 | 입력, 활동, 산출물, 검증, 책임, 선후행관계 |
| 연차 게이트 | 연차별 산출물, 합격조건, 다음 단계 진입조건 |
| KPI | 기준선, 목표, 산식, 대상, 표본·기간, 검증주체 |
| 실증·운영 | 현장, 사용자, 운영기간, 장애·안전·보안 대응 |
| 사업화 | 첫 고객, 제공형태, 구매·계약, 운영·유지관리, 확산 |
| 불확실성 | 확인, 가정, 결정 필요, 자료 필요와 영향 |

## 7. 초안 구체성 기준

다음 중 필요한 질문에 답하지 못하는 문단은 일반론으로 보고 다시 씀

- 무엇을 만들거나 바꾸는가
- 누가 사용·개발·검증·운영하는가
- 어떤 데이터·설비·선행 산출물을 입력으로 쓰는가
- 어떤 순서와 방식으로 작동하는가
- 어떤 산출물과 기록이 남는가
- 무엇과 비교하여 성공을 판단하는가
- 실패·지연·장애가 생기면 어떤 대안을 쓰는가
- 다음 연차·실증·구매 결정으로 어떻게 이어지는가

기술용어와 형용사를 늘리는 대신 관찰 가능한 행동, 인터페이스, 산출물과 합격조건을 씀
