# 목적

새 자료를 기존 규칙에 무조건 덧붙이지 않고, 근거유형과 적용범위를 구분하여 Skill을 안전하게 고도화함

# 작업 시작 전 사용자 이해 확인

다른 모든 절차보다 먼저 [작업 시작 전 사용자 이해 확인](references/06-user-confirmation-gate.md)을 적용함. 최초 응답에서는 요청 목적·예상 근거자료·분석 및 변경 범위·산출물·핵심 가정을 설명하고, 사용자가 그 설명을 본 뒤 별도 메시지로 동의할 때까지 자료·스킬 원본 탐색, 분석과 파일 수정을 시작하지 않음. 수정사항이나 실질적인 범위 변경이 있으면 이해 내용을 다시 설명하고 재확인함. 이 확인은 규칙 승격·보류와 실제 스킬 변경에 필요한 후속 승인을 대체하지 않음

# 진행 기본값

- 현재 대화와 작업 폴더에서 기존 스킬 원본과 새 근거자료를 먼저 찾고, 이미 제공된 파일을 다시 요청하지 않음
- 원문에서 확인 가능한 추출·분류·충돌 분석을 먼저 수행하고, 자료가 부족한 판단만 보류함
- 사용자 요청이 근거 분석에 그치면 스킬 파일을 수정하지 않으며, 업데이트 요청이 명시된 경우에만 새 버전 또는 변경본을 만듦
- 원문 자료는 수정하지 않고, 배포용 스킬에는 기밀·개인정보·민감 수치를 복제하지 않음

# 핵심 원칙

[근거 누적·규칙 승격 정책](references/01-update-policy.md)을 최우선으로 적용함

- 공식 규칙, 평가의견, 작성기관 대응, 실제 결과를 분리함
- 같은 사업의 여러 세부과제 반복은 사업 프로파일 근거임
- 서로 다른 사업군에서도 반복되거나 공식 지침에 있는 경우에만 범용 코어 승격을 제안함
- 평가기관의 반영내용은 정답이 아니라 대응 사례임
- 구체적 숫자와 기관명은 규칙으로 승격하지 않음
- 기존 규칙과 충돌하면 덮어쓰지 않고 충돌을 기록함

# 입력 자료 분류

1. 공식 공고·RFP·양식·배점표·Q&A
2. 실제 제출본과 버전
3. 선정·탈락·후속평가 결과
4. 평가위원 의견 원문
5. 작성기관 반영내용
6. 실증·공인시험·성과 결과
7. 사용자 피드백과 실제 사용 중 발견된 오류

# 업데이트 절차

## 1. 자료 인벤토리

- 자료명, 사업명, 연도, 전문기관, 결과, 버전, 페이지를 기록함
- 중복 파일과 최신본을 구분함
- 기밀·개인정보를 확인함

## 2. 원문 단위 추출

평가의견 한 건을 다음 필드로 추출함

- 원문
- 평가대상 위치·주제
- 요구의 핵심
- 공식 근거 여부
- 작성기관 대응
- 실제 해소 여부를 확인할 후속자료
- 적용 가능한 사업·분야

## 3. 기존 렌즈와 매핑

- 기존 렌즈와 같은 문제인지
- 새 렌즈가 필요한지
- 긍정평가 패턴인지
- 단순 편집 문제인지 구조·기술·사업화 문제인지

## 4. 근거등급과 배치

- A 공식 규칙 → 코어 또는 공고 프로파일
- B 독립 사업 반복 → 코어 후보
- C 동일 사업 반복 → 사업 프로파일
- D 단일 관찰·대응 → 후보 또는 사례

## 5. 변경안 생성

다음을 분리하여 제시함

- 코어 변경안
- 기존 프로파일 변경안
- 신규 프로파일
- 후보 규칙
- 삭제·완화할 규칙
- 충돌과 미해결 질문

사용자 확인 전 범용 코어를 자동 승격하지 않음

## 6. Skill 수정

- SKILL.md는 짧게 유지하고 상세근거는 references로 이동함
- name·description의 호출경계를 유지함
- 모든 참조경로를 검증함
- 숫자 사례는 `예시`로 표시함
- 변경된 동작에 맞는 테스트 사례를 추가함

## 7. 결과물

1. 근거 인벤토리
2. 신규·변경 근거 레지스터
3. 승격·보류·충돌 의사결정표
4. 수정된 프로파일·참조파일
5. 변경된 Skill 폴더 또는 설치 가능한 ZIP
6. CHANGELOG
7. 아직 부족한 근거와 다음 수집 우선순위

# 품질 게이트

- 단일 사업 사례가 범용 코어로 들어갔는가
- 평가의견과 반영내용을 섞었는가
- 선정 결과와 특정 문장의 인과를 단정했는가
- 예시 숫자를 기본 목표로 만들었는가
- 반대 사례를 삭제했는가
- 기존 Skill의 호출경계를 넓혀 충돌하게 했는가
- 새 규칙을 검증할 테스트가 있는가
