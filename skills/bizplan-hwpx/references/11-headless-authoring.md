# 경량 HWPX 생성 절차

확정된 Markdown 본문과 표지 정보가 모두 준비됐을 때만 사용한다. 일반 산출물의 문안이 미확정이면 [본문 품질 검토](14-general-artifact-content-quality.md)에 따라 자료와 질문·답변으로 먼저 준비한다. 사업계획서 내용 준비에만 `bizplan-draft`를 사용하며 공식 양식 경로를 유지한다.

## 생성 전 내용 검토

일반 산출물은 14번 참조로 전체 Markdown의 독자용 내용·근거·미확정 사항을 검토한 뒤 생성한다. 작성 지침·대화 동의·생성 검증 기록은 대화나 별도 작업 기록에 둔다. 계약·양식이 요구하는 출처·한계·검토 및 승인 이력은 삭제하지 않는다. 생성기와 `check_headless_artifact.py`는 내용의 타당성이나 요구사항의 충분성을 자동 판정하지 않는다.

```powershell
python <스킬>/scripts/build_headless_artifact.py `
  --content "본문.md" `
  --agency "발주기관" `
  --program "상위 사업명" `
  --project-number "과제번호" `
  --project "세부 사업명" `
  --title "산출물 제목" `
  --document-type "요구사항정의서" `
  --artifact-version "v0.1" `
  --revision-note "최초 작성" `
  --revision-author "작성자" `
  --revision-date "2026-09-02" `
  -o "DXS-AX-REQ-AX1_요구사항정의서-20260902-v0.1.hwpx"
```

별도 `--template`은 받지 않는다. 포함된 승인 템플릿만 사용한다.

## 개정 이력과 파일명 버전

- `--artifact-version`은 프로젝트의 현재본·외부 `산출물_버전이력.md`와 대조해 확정한 값을 사용한다. 생성기가 마지막 행만 보고 다음 버전을 추정하지 않는다.
- 출력 파일명은 `DXS-[사업코드]-[문서유형]-[파일제목]-[YYYYMMDD]-vX.Y.hwpx`를 사용한다. 파일명 날짜와 버전은 개정 이력 최신 일자·버전과 정확히 같게 한다. 예: `DXS-AX-REQ-AX1_요구사항정의서-20260902-v0.1.hwpx`.
- 문서유형은 `STD/MGT/BUD/REQ/DES/DEV/TST/DAT/RPT/EVD/SOP/MIN` 중 주 기능 하나를 사용한다. 사업코드나 문서유형이 불명확하면 팀 기준 용어사전을 확인하고 사용자에게 물으며 임의 코드를 만들지 않는다.
- `--revision-note`의 한글은 실제 UTF-8 문자로 기록하고, 작성자가 확정된 경우에만 `--revision-author`를 같은 방식으로 입력한다. 확인자 칸은 자동 입력하지 않는다.
- 개정 이력표가 없거나 빈 행이 없고, 기존 행이 부분 입력·중복·역순이거나 파일명이 불일치·복수 버전 토큰이면 파일을 쓰기 전에 중단한다.
- 기존 출력 경로가 있으면 덮어쓰거나 삭제하지 않는다. 다른 새 버전 경로를 확정한 뒤 다시 실행한다.
- 경량 생성 후보를 검증한 뒤에만 같은 버전의 PDF·프리뷰·readback과 함께 승격하고 외부 버전 이력을 갱신한다.

## 한글 입력 보존

- 표지 정보와 Markdown의 확정 한글은 입력된 실제 문자 그대로 사용한다.
- 한글을 유니코드 이스케이프, 숫자 문자참조, 영문 음역 또는 ASCII 대체문자로 사전 변환하지 않는다.
- JSON이나 로그를 거칠 때도 `ensure_ascii=False`와 UTF-8을 사용해 사람이 한글을 그대로 읽을 수 있게 한다.
- XML 생성에서는 `&`·`<`·`>` 같은 문법 충돌 문자만 이스케이프하고 한글은 이스케이프하지 않는다.
- 생성 후 표지·본문·목록·표 셀 readback을 확정 입력과 문자 단위로 대조한다. 서로 다르면 출력 파일을 승격하지 않는다.

## Markdown 지원

| 입력 | 결과 |
|---|---|
| `# 1. 제목` | 수준 1, 앞 공백 0개, 15pt, 새 쪽 시작 |
| `## 1.1 제목` | 수준 2, 앞 U+0020 공백 3개, 12pt |
| `### 1.1.1 제목` | 수준 3, 앞 U+0020 공백 5개, 10.5pt |
| `#### 1.1.1.1 제목` 이상 | 번호 접두어를 제거하고 앞 공백 없는 `•` 본문 목록과 hanging indent로 전환 |
| 일반 문단 | 10pt, 160% |
| `- 항목` | 앞 공백 없는 `•` 본문 목록, 왼쪽 4000·첫 줄 -800 HWPUNIT |
| `1. 항목`, `10. 항목` | 번호 보존, 접두어 폭에 맞춘 hanging indent, 후속 줄 본문 정렬 |
| Markdown 표 | 기본 글자처럼 취급, 최종 계산 높이가 한 쪽 초과인 표만 해제/CELL; 축 중앙·나머지 왼쪽·160% |

그림·쪽번호·병합 셀·각주·미주는 생성하지 않는다. 필요한 문서는 upstream `hwpx` 편집 경로를 사용한다.

## 생성 후 검증

생성기는 구조·서식 자동검사를 통과한 경우에만 최종 경로에 파일을 둔다. 이어서 다음을 수행한다.

1. `check_headless_artifact.py` 재검사
2. 확정 한글과 HWPX 내부 XML·readback의 실제 문자 일치 검사. 일반 산출물은 14번 참조로 readback 전체의 내용 품질도 별도 재검토하고, 수정 시 변경 부분뿐 아니라 전체의 반복·정합성을 다시 확인함
3. 제목 수준 1~3의 앞 공백 0·3·5개와 `개요 1`·`개요 2`·`개요 3` 스타일 연결, 제목 문단 들여쓰기 중복 부재 검사
4. 본문 목록 텍스트의 앞 공백 부재, 왼쪽 4000·첫 줄 -800 HWPUNIT, 첫 줄 글머리표 3200·후속 줄 본문 4000 HWPUNIT의 `lineseg` 일치 검사
5. 본문·목록 뒤 수준 2~3 제목 `prev=1200`, 표↔본문·목록·제목·표의 12pt 단일 경계, 연속 제목·명시적 새 쪽 예외 검사. inline은 다음 문단 윗간격, floating은 표 바깥 여백을 사용하며 합산 중복하지 않음
6. 표 1행·1열의 가로 가운데·세로 중앙, 나머지 셀의 가로 왼쪽 맞춤 검사
7. 빈 문단이나 파란색 검토 문구·`##############################` 마커 잔여 부재 검사
8. 개정 이력의 최신 버전·개정일자·개정내역·작성자 입력 여부와 DXS 파일명 날짜·버전·문서유형 코드 일치 검사
9. upstream `hwpx`의 구조·open-safety·readback 검증
10. `render_preview` 검토
11. 제출 후보라면 Windows 한컴에서 전체 페이지 관찰

추가 회귀 검증은 합성 Markdown으로 수행한다. 표의 최종 열 너비를 바꿨다면 셀 `lineseg`·행 높이·표 높이·앵커 캐시가 모두 재계산됐는지 검사한다. 짧은 표를 쪽 하단에 두어도 inline이 유지되는지, 한 쪽 초과 표만 해제/CELL인지, 긴 표 마지막 조각 뒤에도 여백이 보이는지 확인한다. 한 셀 자체가 한 쪽을 넘으면 내용을 나누기 전에는 생성물을 발행하지 않는다. 번호 목록의 앞 공백 부재·접두어 폭에 맞는 왼쪽/첫 줄 값과 후속 줄 위치도 검사한다.

`layout_headless_artifact.py`는 위 규칙의 공용 계산 모듈이며 외부 문서 직접 편집기가 아니다. 기존 사용자 문서를 이 모듈이나 formatter에 바로 넣어 일괄 교정하지 않는다. 승인 템플릿 불가침 영역·기존 산출물 버전 관리 규칙을 지키고, 기존 문서 수정은 원본 보존·사용자 동의·upstream 검증 경로를 사용한다.

경량 생성 성공은 `structure_verified` 이전의 자동 생성 성공일 뿐이며, 한컴 시각 검증이나 제출 준비 완료를 뜻하지 않는다.
