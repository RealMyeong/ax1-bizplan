# 일반 산출물 본문 품질

AX1 일반 산출물의 신규 본문·내용 수정·내용 검토에 적용한다. 서식만 수정하도록 요청받았다면 본문을 임의로 다시 쓰지 않고 발견한 내용 문제만 별도 보고한다. 사업계획서는 기존 전용 스킬을 사용한다. 계약·고객의 필수 구조와 기재 의무가 이 참조의 기본값보다 우선한다.

## 작성 과정과 독자용 내용의 경계

- 작성 규칙, 에이전트의 자료 열람·생성·검증 과정, 채팅 동의와 작업 진행 설명은 대화 또는 별도 작업 기록에 둔다. 문서의 목적·현황·요구사항을 대신하는 본문으로 넣지 않는다.
- 출처, 분석 범위·한계, 근거 부족, 미결정 항목, 계약상 검토·승인 이력은 독자가 판단하는 데 필요하면 본문·해당 표·주석 등 양식에 맞는 위치에 보존한다. 채팅에서 작성에 동의한 것을 고객의 내용 승인으로 기록하지 않는다.
- 특정 단어를 금지어로 삼아 자동 삭제하지 않는다. `자료`, `확인 필요`, `승인`이 있다는 이유만으로 오류가 아니다. 인용문·교육 문서·작성 지침 자체가 요청된 산출물인 경우 그 설명이 본문일 수 있다.

예를 들어 “자료를 임의로 채우지 않는다”는 작성자의 작업 규칙이다. 반면 “정지 판정 임계값은 미확정이며 설비 담당자의 결정이 필요하다”는 해당 요구사항의 구현에 영향을 주므로 남긴다. “문서 작성 동의는 고객 승인이 아니다”라는 대화 설명 대신 실제 승인 상태가 필요하면 근거가 있는 상태만 기록한다.

## 자료에서 본문으로

- 확인된 사실은 업무 대상 중심으로 쓴다. 근거가 있는 “가상 조립라인은 공정 A~C로 구성된다”를 매번 “제공자료에는 … 기재되어 있다”로 시작하지 않는다. 출처는 추적 가능한 위치에 남긴다.
- 직접 확인되지 않은 사실·추정·자료 간 충돌은 그 한정 표현을 보존한다. 문장을 간결하게 고치려다 추정을 사실로 바꾸지 않는다. 문서 전체의 막연한 면책 문구보다 영향을 받는 항목에 무엇이 미확정인지와 필요한 자료·결정을 붙인다. 담당이 알려지지 않았으면 이름을 만들지 않는다.
- 현장분석·요구사항정의서는 확인된 현황 → 구체적 문제 → 개선 방향 → 시스템 요구사항이 추적되도록 연결한다. 이 연결은 논리 점검이며 모든 문서의 고정 목차가 아니다. 회의록·결과보고서 등은 그 목적과 지정 구조를 따른다.
- “체계적으로 관리한다”만 반복하지 말고 대상·행위·조건을 자료 범위 안에서 구체화한다. 자료가 기능 도출을 뒷받침하지 않으면 새 기능을 확정하지 않고 제안/결정 필요로 분리한다. 수치·임계값·책임·승인을 임의로 채우지 않는다.

예: 근거가 “설비별 신호 대응관계 미정”이고 기존 요구사항이 “설비별 상태 집계”라면 “설비별 상태 집계를 위해 설비 식별자와 상태 신호의 대응관계를 정의해야 한다. 대응관계는 미확정이며 확정 전 집계 대상 연결을 완료할 수 없다”처럼 연결한다. 기존 요구사항과 무관한 자동 제어 기능까지 만들어 넣지 않는다.

## 식별자·약어와 수정의 경계

- 기존 요구사항 ID와 기능 의미를 보존한다. 오기·충돌·변경 필요를 발견하면 사용자에게 확인하며 임의 재번호·기능 확대를 하지 않는다. 보존 여부와 분석의 충분성·중복 여부는 별개로 검토한다.
- 독자가 알아야 할 코드·약어는 최초 사용 또는 용어/코드 표에서 의미를 설명한다. 구조가 자료에 정의되어 있으면 각 부분의 의미와 다른 식별자와의 관계, 필요한 읽기 예시를 덧붙인다. 약어의 풀이나 코드 구조가 없으면 추측하지 않는다.
- 요구사항 ID, 설비 ID, 신호 주소, 문서번호는 다른 식별 체계다. 같은 접두어나 숫자라는 이유로 동일시하거나 대응관계를 만들어내지 않는다. 가상 예시는 실제 운영 값과 구분한다.

## 내용 검토와 재검토

생성 전 전체 Markdown과 생성 후 전체 readback을 각각 검토한다. 내용 수정 후에도 전체를 다시 읽어 같은 지침 혼입·반복 설명·서로 다른 값이 다른 절에 남지 않았는지 확인한다. 원문 그대로의 전사는 요청 범위 밖의 개작 없이 내용 문제를 보고하는 데 그친다.

1. 독자에게 필요한 사실·분석·결정인가, 작성자에게 하는 작업 지시인가?
2. 문서 목적에 맞는 논리 연결이 있으며 추적 가능한 근거와 필요한 한계를 보존했는가?
3. 기존 ID·기능 의미가 유지되고 코드·약어의 역할이 구별되는가?
4. 구체화가 근거 없는 수치·기능·책임·승인을 추가하지 않았는가?
5. 수정 후 전체의 중복·모순과 미결정 항목을 다시 확인했는가?

대화 또는 별도 검토 기록에 검토 범위, 수정 사항, 근거/결정 필요 항목과 `내용 검토 완료`·`내용 검토 보류`·`내용 검토 미수행`을 기록한다. 해결되지 않은 중요한 근거·결정 문제가 있으면 보류하며 제출 준비 완료로 올리지 않는다. 이 기록을 독자용 본문에 그대로 붙이지 않는다.

`check_headless_artifact.py`의 구조·서식 검사, 문자 readback 일치, 한컴 시각 검증은 별도 결과다. 어느 하나의 통과도 다른 검토를 대신하지 않는다. 이 참조는 맥락을 읽는 검토 기준이며 자동 의미 판정기나 금지어 차단기가 아니다.
