# 문서 정보·개정 이력·사용자 접근 권한

승인 AX1 일반 산출물에 적용한다. 공식·고객 양식은 그 필수 항목과 upstream 편집 경로를 유지한다. 승인 템플릿 원본 파일을 수정하지 않는다.

## 작성 전 질문

최초 이해 확인의 별도 동의 뒤, 본문 설계 질문과 묶어서 다음을 확인한다. 이미 제공된 정보는 요약 확인하며 같은 질문을 반복하지 않는다.

- 제목과 문서 유형: 예를 들어 제목 `현재 수집 데이터 정의서`, 유형 `데이터 정의서`. 제목에 유형이 이미 포함됐으면 별도의 큰 유형 문구는 중복 표시하지 않는다고 설명한다.
- 작성자·검토자·사업책임자: 각각 소속·성명, 실제로 확정된 날짜. 미정은 비워 두거나 추가 자료를 받는다. 직함·사람을 임의 지정하지 않는다.
- 이번 작업이 신규인지 개정인지, 같은 산출물군의 기준본 위치·버전·SHA-256, 기존 개정 이력, 이번 변경 요약과 새 버전·개정일자.
- 실제 문서를 열 사용자와 최종 저장 경로. 자동화 계정과 사용자가 다를 수 있음을 고려한다.

질문 예: “작성자·검토자·사업책임자의 소속과 성명을 알려주세요. 미정인 역할은 비워둘까요? 기존 문서 개정이면 기준본과 이번 변경 요약도 알려주세요. 검토·승인 날짜는 실제 완료된 경우에만 기재합니다.”

검토자 지정은 검토 완료가 아니다. 서명·고객 승인·확인자는 자동 작성하지 않는다. 개정 시 기존 담당자 소속·성명은 이어받되 변경 여부를 확인하고, 과거 검토·승인 날짜·서명을 새 버전에 복사하지 않는다. 과거 개정표에 있는 작성자·확인자 기록은 해당 과거 이력으로 그대로 보존한다.

## 생성기 입력

확인한 문서 정보는 프로젝트 제한 작업 폴더의 UTF-8 JSON으로 저장해 `--document-info`에 전달한다. 실제 성명·소속 JSON은 저장소·공개 테스트에 넣지 않는다.

```json
{
  "작성자": {"소속": "합성팀", "성명": "합성 작성자"},
  "검토자": {"성명": "합성 검토자"},
  "사업책임자": {}
}
```

역할별 `소속`·`성명`·`날짜`만 지원한다. 날짜는 확정된 `YYYY-MM-DD`만 입력한다. 미입력 값은 빈 칸으로 두며 서명 입력은 지원하지 않는다. 문서 정보의 작성자와 `--revision-author`가 충돌하면 멈춘다.

표지의 제목과 유형을 공백 제외 후 비교해 제목이 유형으로 끝나면 유형 슬롯만 빈 표시로 둔다. 전체 제목, 본문 제목, 목차의 정당한 반복은 삭제하지 않는다. 표지 위치·글꼴·로고·표 구조는 보존한다.

## 개정 이력 누적

신규 문서의 기본 최초 내부본은 v0.1이다. 개정은 `--previous-artifact <기준본.hwpx> --previous-sha256 <확인한 해시>`를 반드시 전달한다. 기준본은 같은 사업코드·문서유형·파일제목의 AX1 문서여야 하며 읽기만 한다. 이전 문서를 템플릿이나 일괄 재서식 대상으로 쓰지 않는다.

이전 개정표의 날짜·버전·개정내역·작성자·확인자를 모두 새 문서로 옮기고 마지막에 이번 개정 1행을 추가한다. 새 버전은 이전보다 커야 하고 날짜가 거꾸로 갈 수 없다. 게시 직전 기준본 해시를 다시 확인한다. 이력 누락·중복·역순·부분 기록·같은 버전·다른 산출물군·파일명 충돌이면 초기화하지 않고 자료·결정을 요청한다. 파일제목 변경이나 이관은 별도 매핑을 확인한 upstream 경로로 처리한다.

현재 승인 양식은 기록 4행이다. 4행 모두 채워진 문서 자체는 유효하지만 다음 개정을 추가하려면 표 확장이 필요하다. 이 경우 기존 이력을 보존하고 upstream에서 새 후보의 표·페이지를 확장·검증한다. 경량 생성기는 표를 임의 복제하거나 과거 행을 삭제하지 않고 출력 전에 중단한다. upstream이 없으면 이력과 수정 후보를 보존하고 `표 확장 검증 대기`로 보고한다. 과거 기록을 지워 생성기 한도를 우회하지 않는다.

## Windows 권한 확인

Windows에서는 임시 파일의 하드링크·이동이 제한된 DACL을 그대로 남길 수 있다. 생성기는 최종 폴더에 새 파일을 배타적으로 생성하고 바이트만 복사해 대상 폴더의 권한을 상속한다. 기존 경로를 덮어쓰지 않고 전후 SHA-256을 비교한다. 복사 도중 파일은 보일 수 있으므로 생성 성공 전에는 열거나 최신본으로 승격하지 않는다.

이 조치만으로 모든 권한 문제가 해결된다고 보장하지 않는다. 상위 폴더 ACL, 파일 잠금·읽기 전용 속성, 보안 프로그램 차단은 별도 확인한다.

1. 생성 전 대상 폴더의 소유자·ACL과 실제 사용자 계정을 확인한다. `Get-Acl -LiteralPath ...`의 명시적 사용자 항목이 없다는 이유만으로 실패라고 단정하지 않는다. 그룹·상속·거부 규칙도 영향을 준다.
2. 생성 후와 최신본 폴더로 전환한 후 각각, 실제 문서 사용자 보안 컨텍스트에서 `scripts/Test-HwpxAccess.ps1 -LiteralPath <최종파일.hwpx> -ExpectedUserSid <확인한 사용자 SID>`를 실행한다. 이 검사는 ACL·내용을 바꾸지 않고 읽기/쓰기 핸들 개방과 전후 해시를 검사한다. 현재 계정과 예상 SID가 다르면 중단한다. 샌드박스 계정의 성공을 사용자 계정의 성공으로 대신하지 않는다.
3. `file_locked`는 문서가 열린 앱을 확인해 사용자가 정상 종료한 뒤 한 번 재검사한다. 프로세스를 강제 종료하지 않는다. `access_denied`이면 파일/부모 권한·읽기 전용·보안 제품 정책을 구분한다. 필요한 실행 권한이 없으면 승인을 요청하고 검증 대기로 둔다.
4. 권한 변경이 필요하면 정확한 파일·사용자·필요 권한과 이유를 설명하고 승인받는다. 필요한 파일에만 읽기·수정을 허용하고, 변경 전 ACL과 파일 해시를 보관한 뒤 동일 사용자 접근·내용 해시를 재검사한다. 명시적 거부나 조직 정책을 우회하지 않는다.
5. `Everyone`·광범위 그룹에 전체 제어, 상위 폴더 재귀 권한 초기화, 소유권 강제 변경, UAC/백신 비활성화, 항상 관리자 실행은 하지 않는다. 파일 경로만 바꿔 제한을 우회하지 않는다.

내용·구조·사용자 접근·한컴 시각 검증은 별도 상태다. 읽기·쓰기 개방 성공은 실제 저장·이름 변경·백신 허용·한컴 조판까지 보장하지 않는다.
