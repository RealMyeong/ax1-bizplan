# 작업 시작 전 사용자 이해 확인

새 작업 요청을 받으면 다른 모든 스킬 절차보다 먼저 사용자가 요청한 내용을 에이전트가 정확히 이해했는지 확인한다. 이 확인은 단순 안내가 아니라 실제 작업 시작 조건이다.

## 1. 최초 응답

최초 응답에서는 사용자의 요청과 이미 대화에 드러난 정보만 사용해 다음을 짧고 구체적으로 설명한다.

1. 이해한 목적
2. 사용할 것으로 예상한 입력자료와 기준
3. 진행할 작업 범위와 진행하지 않을 범위
4. 예상 산출물
5. 중요한 가정·위험·추가 승인이 필요한 지점

마지막에는 `제가 이해한 내용이 맞으면 진행하겠습니다. 수정할 부분이 있으면 알려주세요.`처럼 명시적인 확인을 요청하고 응답을 끝낸다.

## 2. 확인 전 금지

사용자가 위 설명을 본 뒤 다음 메시지에서 명시적으로 동의하기 전에는 다음 행동을 하지 않는다.

- 작업 폴더·첨부파일·문서·저장소의 목록 조회, 검색, 열기, 읽기, 파싱
- 셸·PowerShell·스크립트·브라우저·웹 검색·Drive·Notion·GitHub·MCP 호출
- 환경·의존성·버전·연결 상태 점검
- 문서 렌더링·변환·비교·검증
- 파일·폴더·문서의 생성, 편집, 이동, 이름 변경, 삭제
- Git 조회·커밋·푸시·태그·릴리스 등 저장소 작업
- 외부 시스템에 쓰기, 메시지 전송, 제출 또는 배포

최초 설명을 만들기 위해 자료를 먼저 확인하지 않는다. 확인 뒤 발견해야 하는 정보는 `진행 승인 후 확인할 항목`으로 밝힌다. 확인하지 않은 파일이나 상태를 확인했다고 표현하지 않는다.

## 3. 유효한 확인

- 이해 설명이 제시된 뒤의 별도 사용자 메시지에 `맞아`, `진행해줘`, `그대로 해줘`처럼 명시적인 동의가 있어야 한다.
- 최초 요청에 `바로 진행`, `질문 없이`, `확인 생략`이 포함되어 있어도 이해 설명 뒤의 별도 동의를 대신하지 않는다.
- 질문, 상태 확인, 추가 정보만 있는 답변이나 뜻이 불분명한 답변은 동의로 추정하지 않는다.
- 사용자가 수정사항을 말하면 반영한 이해 내용을 다시 설명하고 다시 확인을 기다린다.

## 4. 재확인

확인된 범위 안의 사소한 구현 선택은 반복 확인하지 않고 진행한다. 다만 작업 중 발견한 사실 때문에 목적, 입력 기준, 수정 대상, 산출물, 외부 영향이 실질적으로 달라지면 작업을 멈추고 변경된 이해 내용을 설명한 뒤 다시 동의를 받는다.

## 5. 다른 승인 절차와의 관계

이 확인은 다음과 같은 후속 승인 절차를 대체하지 않는다.

- `bizplan-draft`의 사업 아이디어·구현 브리프 확정
- HWPX 모의 편집 뒤 실제 반영, 재개방과 시각 검증
- 원본 덮어쓰기·삭제 등 파괴적 작업
- 커밋·푸시·배포·제출·외부 전송 등 외부 상태 변경
- 승인되지 않은 수치·기관 역할·대외 표현의 사람 확인

읽기 전용 검토, 제출 전 점검, 작업공간 준비, 근거 업데이트에도 같은 최초 확인을 적용한다. 명확한 수행 불가·안전 제한을 알리는 답변은 작업을 시작한 것으로 보지 않지만, 실제 대안을 실행하려면 먼저 이 확인을 거친다.
