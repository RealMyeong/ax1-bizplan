# 산출물 최신본·이전버전 관리

새 버전의 산출물을 만들 때 주 작업공간에는 현재 사용할 최신본만 남기고, 이전본은 프로젝트 안의 `98_이전버전`에서 다시 확인할 수 있게 보관함

## 1. 적용 범위와 용어

- 적용 대상은 에이전트가 새로 만들거나 수정한 DOCX·HWPX·PDF·PPTX, 검토보고서, 반영대장과 그 버전에 종속된 프리뷰·검증기록 등 `관리 산출물`임
- `00_공고_RFP`부터 `07_예산_일정`, `90_참고자료`에 있는 공고문·원본 양식·근거자료·사용자 원본은 산출물 버전 정리 대상으로 취급하지 않음
- 서명본, 접수증, 승인기록처럼 서로 다른 사건을 증명하는 파일은 같은 산출물의 구버전으로 보지 않음
- 접수번호·서명·제출시각 또는 접수증이 특정 파일 해시와 연결된 실제 제출 완료 파일도 사건 증거임. 자동으로 이동·이름변경·덮어쓰기하지 않고, 정정이 필요하면 별도 `정정·재제출 후보` 산출물군을 만듦
- `산출물군`은 목적과 사용처가 같은 버전 계열임. 사업계획서 본문, 발표자료, 검토보고서, 검토의견 반영대장과 제출증빙은 서로 다른 산출물군으로 관리함
- `버전 묶음`은 같은 버전의 주 파일과 PDF·프리뷰·매핑표·검증기록처럼 함께 보아야 하는 연관 파일의 집합임. 확장자가 다르다는 이유만으로 서로를 구버전으로 판단하지 않음
- `현재본`은 관련 검증을 통과했거나 사용자가 기준본으로 지정한 버전임. 파일 수정시각이나 파일명 숫자만으로 현재본을 확정하지 않음
- 검증 기준은 작업단계에 맞춤. `08_작성중`·`09_검토_수정`은 파일 열림, 의도한 변경, 구조·readback과 치명적 레이아웃 오류가 없는지를 확인하고 명시적으로 관리되는 미확정 항목은 허용할 수 있음. `10_제출본`은 빈칸·수치·형식·시각 검증과 사람 승인까지 충족해야 함

## 2. 저장 위치

```text
08_작성중/                         산출물군별 현재 작성본
09_검토_수정/                     산출물군별 현재 검토·수정본
10_제출본/                        산출물군별 현재 승인·제출 후보
98_이전버전/
  08_작성중/<산출물군>/<버전>/    작성 단계에서 물러난 버전 묶음
  09_검토_수정/<산출물군>/<버전>/ 검토·수정 단계에서 물러난 버전 묶음
  10_제출본/<산출물군>/<버전>/    물러난 미제출 승인 후보 버전 묶음
  산출물_버전이력.md               현재본과 보관본의 경로·해시·상태
99_임시작업/                      새 버전 검증 중간파일과 재생성 가능 파일
```

- 하나의 산출물군에는 `08_작성중`, `09_검토_수정`, `10_제출본`을 통틀어 현재본 한 묶음만 둠. 단계가 올라가면 이전 단계의 같은 산출물군도 보관함으로 이동함
- 서로 다른 산출물군의 현재본은 함께 남길 수 있음. `최신본만 유지`를 프로젝트 전체 파일 하나만 남긴다는 뜻으로 해석하지 않음
- 사용자가 기관별·제출처별 대안이나 병렬안을 의도적으로 유지하면 각각 별도 산출물군 ID를 지정함
- 이전 버전은 삭제하지 않고 원래 단계가 표시되는 보관 경로로 이동함. 단, 실제 제출 완료 파일과 그 사건 증거는 자동 이동하지 않음
- `98_이전버전`의 파일은 이력 보존 자료이며 그 자리에서 수정하거나 다시 보관 대상으로 삼지 않음
- 다른 산출물군도 같은 의미 변경의 영향을 받으면 최신 산출물 간 내용 연동 규칙에 따라 산출물군별 독립 버전은 유지하되 하나의 연동 ID와 전환 트랜잭션으로 묶음

## 3. 파일명과 버전

### 3.1 AX1 기본 파일명

별도 제출처·고객 필수 규칙이 없는 새 관리 산출물은 다음 형식을 사용함

```text
DXS-[사업코드]-[문서유형]-[파일제목]-[YYYYMMDD]-vX.Y.[확장자]
```

예: `DXS-AX-STD-AX_통합_용어사전-20260902-v0.2.docx`

- `DXS`는 발행 회사 코드 고정값임
- `사업코드`는 승인된 짧은 영문 대문자·숫자 코드를 사용함. 공식 사업명 전체나 에이전트가 만든 임시 약어를 쓰지 않음
- `문서유형`은 아래 기준표의 3자 영문 대문자 코드를 사용함
- 세그먼트 경계는 하이픈 `-`, `파일제목` 내부 단어 경계는 밑줄 `_`을 사용함. 파일제목에는 공백과 하이픈, Windows 금지문자 `/ \\ : * ? " < > |`를 넣지 않음
- 파일제목은 역할과 범위를 식별할 수 있게 작성하되 사업코드·문서유형을 불필요하게 반복하지 않음. 협력사명·개인명·보안등급과 `최종`, `진짜최종`, `final2` 같은 상태어를 넣지 않음
- `YYYYMMDD`는 내용이 실제로 수정·확정된 한국 날짜임. 단순 이동·복사만으로 날짜를 바꾸지 않음
- 관리 산출물 버전은 정확히 `vX.Y` 두 숫자 성분으로 기록함. 문서 내부 개정 이력, 주 파일, PDF·프리뷰·readback과 외부 버전 이력에도 같은 값을 사용함
- 확장자는 실제 파일 형식과 일치시킴

### 3.2 사업코드와 문서유형 코드

코드의 관리 원본은 팀 제한 작업공간 `01_최신산출물/00_AX공통/`에 있는 최신 `DXS-AX-STD-AX_통합_용어사전-*.docx`임. 저장소와 배포 ZIP에는 이 내부 DOCX를 포함하지 않고, 승인된 코드·정의의 비식별 스냅샷만 유지함. 현재 스냅샷은 `2026-09-02 / v0.2`를 기준으로 함

| 사업코드 | 적용 범위 |
|---|---|
| `AX` | 특정 외부사업에 종속되지 않는 AX팀 공통 표준·양식·가이드 |
| `PILAM6` | PI-LAM 세부과제 6 |

| 문서유형 | 원어 | 적용 범위 |
|---|---|---|
| `STD` | Standard | 공통 표준·용어사전·명명규칙 |
| `MGT` | Management | 계획·WBS·실행관리·리스크·변경관리 |
| `BUD` | Budget | 사업비·예산·구매·집행·잔액 관리 |
| `REQ` | Requirements | 요구사항·제공조건·인터페이스 요구 |
| `DES` | Design | 구성도·상세설계·BOM·배선·사양 |
| `DEV` | Development | 소스·모델·펌웨어·빌드·시제품 |
| `TST` | Test | 시험계획·절차·시나리오·결과·검수 |
| `DAT` | Data | 데이터셋·데이터사전·수집로그·기준선 |
| `RPT` | Report | 진도·기술·최종보고·발표자료 |
| `EVD` | Evidence | 구매·납품·검수·정산·사진 증빙 |

| `MIN` | Minutes | 회의록·결정·후속조치 |

- 코드가 기준표에 없거나 두 코드가 모두 적합해 보이면 에이전트가 임의로 확정하지 않고 사용자에게 사업코드·주 문서유형을 확인함
- 용어사전이 개정되면 승인된 최신 버전의 변경 내용을 검토한 뒤 이 스냅샷과 관련 테스트를 함께 갱신함

### 3.3 전환과 예외

- 기존 산출물은 일괄 개명하지 않음. 링크·참조가 깨질 수 있으므로 다음 정식 개정에서 새 규칙의 다른 파일명으로 한 번 전환하고 이전 파일명을 `산출물_버전이력.md`에 기록함
- 제출기관·계약·고객이 파일명을 명시한 경우 그 필수 규칙이 AX1 기본 파일명보다 우선함. 예외 사유와 실제 제출 파일명을 이력에 기록하고 내부 작업본·검증본에는 가능한 범위에서 AX1 식별자를 유지함
- 같은 산출물의 DOCX·HWPX·PDF·PPTX·프리뷰는 확장자를 제외한 기본 파일명과 버전 식별자를 맞춤. 제출처 규칙 때문에 다르면 매핑을 이력에 기록함
- 기존 규칙의 파일을 읽기·검토만 할 때는 이름을 자동 변경하지 않음. 새 파일을 만들거나 정식 개정본으로 승격할 때 기본 규칙을 적용함

### 3.4 버전 묶음 안전 규칙

- 같은 버전 표기로 내용이 다른 파일을 만들지 않음. 내용이 달라지면 버전을 올림
- 한 버전 묶음의 연관 파일에는 같은 버전 식별자를 사용함
- 승인 양식에 개정 이력표가 있는 관리 산출물은 문서 내부 최신 개정 버전, 주 파일 이름, PDF·프리뷰·readback 등 버전 묶음과 `산출물_버전이력.md`의 버전을 같게 유지함. 자동 생성기가 버전을 임의로 올리지 않고 이 절차에서 확정한 새 버전을 입력으로 받음
- 문서 내부 개정 이력·파일명·이력표·사용자 지정 기준본이 서로 다르거나 파일명에 버전 토큰이 여러 개이면 후보를 쓰거나 이름을 바꾸기 전에 중단함
- 개정 이력 자동 기록은 해당 양식에 승인된 표와 빈 행이 있을 때만 허용함. 기존 행의 부분 입력·중복·역순·잘못된 버전, 표 포화 또는 구조 불일치는 자동 보정하지 않음
- 버전 번호, 사용자 지정 기준본과 검증 결과가 충돌하면 자동으로 최신본을 정하지 않음. 새 파일은 `99_임시작업`에 두고 사용자에게 기준을 확인함
- 보관 대상 경로가 이미 존재하면 덮어쓰지 않음. 해시가 같아도 임의 삭제하지 않고, 필요하면 보관시각 접미사를 붙인 새 경로를 사용해 이력표에 사유를 기록함

## 4. 새 버전 전환 절차

실제 파일을 새로 만들거나 수정할 때 다음 순서를 지킴

1. 작업 전 `08_작성중`, `09_검토_수정`, `10_제출본`과 `산출물_버전이력.md`를 확인해 산출물군, 현재본과 연관 파일을 식별함
2. 새 버전은 기존 파일과 다른 이름으로 만들고, 가능하면 `99_임시작업/버전전환/<산출물군>/<새버전>`에서 먼저 생성함
3. 작업단계와 형식에 맞는 구조·내용·렌더·재개방 검증을 끝냄. 개정 이력표가 있는 산출물은 문서 내부 최신 개정 버전, 주 파일과 연관 파일 이름의 버전이 새 후보 버전과 같은지도 확인함. 해당 단계의 검증에 실패하거나 현재본 전환을 막는 Gate가 남으면 기존 현재본을 이동하지 않음
   - 후보가 다른 현재 산출물의 내용에도 영향을 주면 이 단계에서 영향 분석과 모든 필수 연동 후보의 형식별 검증을 완료함. 필수 후보 하나라도 실패하면 어느 산출물군도 부분 승격하지 않음
4. 현재본과 새 버전 묶음의 파일 목록, 프로젝트 기준 상대경로와 SHA-256을 기록함. 이동 전 `99_임시작업/버전전환/<산출물군>/<새버전>/recovery-manifest.json`에 산출물군·버전, 원래 경로, 보관·승격 대상 경로, 파일 해시와 작업 전 이력표 사본 경로를 남김
5. 이동 전에 보관 대상의 절대경로가 프로젝트의 `98_이전버전` 안인지 확인하고, 대상 파일이 편집기에서 열려 있거나 클라우드 동기화 충돌·다른 작업자의 변경 중이 아닌지와 이름 충돌 여부를 점검함
6. 복구 명세를 만든 뒤 기존 현재본의 버전 묶음을 원래 단계에 대응하는 보관 경로로 이동함. 파일별 SHA-256과 읽기 가능 여부를 다시 확인함
7. 검증된 새 버전 묶음을 알맞은 주 작업공간에 두고 파일별 SHA-256과 읽기 가능 여부를 다시 확인함
8. 작업 전 이력표 사본을 보존한 상태에서 갱신안을 먼저 검증한 뒤 `산출물_버전이력.md`의 이전 행은 `보관`, 새 행은 `현재`로 바꿈. 같은 산출물군의 `현재` 행이 하나인지와 기록된 경로·해시가 실제 파일과 일치하는지 확인함
9. 6~8단계에서 파일 이동·승격·검증·이력표 갱신 중 하나라도 실패하면 더 진행하지 않고 복구 명세에 따라 새 묶음과 이미 옮긴 기존본을 작업 전 위치로 되돌리고, 필요하면 작업 전 이력표 사본을 복원한 뒤 SHA-256을 재확인함. 복구 대상 경로에 예상하지 못한 파일이 생겼으면 덮어쓰지 않고 중단함. 자동 복구까지 실패하면 파일을 추가로 이동하지 않고 양쪽의 정확한 위치와 사람의 복구 순서를 보고함
10. 완료 보고에 현재본, 보관한 이전본, 보관 위치, 검증 결과와 예외를 포함함

`recovery-manifest.json`은 최소한 `schemaVersion: "ax1.artifact-recovery/v1"`, `artifactFamily`, `newVersion`, `ledgerPath`, `ledgerBackupPath`와 `files` 배열을 포함함. 각 파일에는 `role`, 이동 전 `source`, 예정 `target`, `sha256`을 프로젝트 기준 상대경로로 기록함

새 버전이 이미 주 작업공간에 생성된 경우에도 검증이 끝나기 전에는 기존본을 보관함으로 옮기지 않음. 전환이 끝날 때만 주 작업공간의 같은 산출물군이 현재본 한 묶음인지 확인함

## 5. 읽기 전용 작업과 예외

- 검토·진단·제출점검만 요청받은 읽기 전용 작업에서는 파일을 이동하거나 이력표를 수정하지 않음
- 사용자가 두 버전을 비교해 달라고 하면 비교용 사본과 임시 결과는 `99_임시작업`에서 다루고, 주 작업공간의 현재본이나 `98_이전버전`의 불변 보관본을 늘리지 않음. 비교 결과 자체를 정식 보존해야 하면 별도 산출물군으로 이름과 버전을 부여해 정상 전환 절차를 적용함
- 산출물군이나 현재본 판정이 모호하거나, 사용자 파일과 관리 산출물을 구분할 수 없거나, 파일 이동이 실패하면 추정해 정리하지 않음
- 사용자가 특정 버전을 다시 사용하려면 보관본을 제자리에서 수정하거나 꺼내지 않고, 그 보관본을 기준으로 새 버전을 만들어 검증한 뒤 현재본으로 전환함
- 프로젝트 밖의 경로, 저장소 루트, 사용자 홈과 Codex 스킬 설치 폴더를 보관 대상으로 사용하지 않음

## 6. 이력표 최소 항목

배포 스킬의 `assets/artifact-version-ledger-template.md`를 사용해 다음 정보를 유지함

- 산출물군과 버전
- `현재 / 보관 / 검증대기` 상태
- 작업 단계와 주 파일·연관 파일의 프로젝트 기준 상대경로
- 주 파일 SHA-256
- 생성·확정 시각과 보관 시각
- 기준 버전, 전환 사유, 검증·복구 메모
